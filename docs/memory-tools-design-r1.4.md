## 1. 定位与目标

### 1.1 这个插件是什么

本插件为**当前项目**提供两类持久信息，并让它们以极低的上下文成本被模型看见：

```text
项目日志：记录发生过什么，**正文不注入**，会话边界只注入标题
长期记忆：记录以后值得复用的结论，会话边界只注入标题
```

两者的关系是单向的提升路径，不是自动同步：

```text
发生事件 → memory_log 写过程 → 得到验证结果 → 需要时 memory_write 提炼为长期记忆
```

不要把所有日志都提升为记忆，也不要把长期记忆当成流水账。

### 1.2 与既有能力的边界

插件不重复造轮子，三条边界必须先说清：

| 既有能力 | 它管什么 | 本插件管什么 |
|---|---|---|
| 技能目录 | 注入**技能名称 + 截断描述**，模型再按需加载正文 | 同一模式：注入**长期记忆标题**（按 `#编号` 取详情）与**日志标题**（按 `J-` 编号取正文） |
| 会话历史检索 | 原始、全量、按事件检索的会话流水 | 项目日志：**人工/模型提炼过**的、面向复用的过程与结论 |
| MCP 记忆服务器 | 外部记忆服务（实体、观察、语义检索） | 本项目内的 Markdown 真相源，不依赖外部服务与 embedding |

一句话：会话历史是"全量原始录像"，项目日志是"这次拍完的场记"，长期记忆是"以后要遵守的结论"。

### 1.3 设计目标

1. **人类可读**：打开 Markdown 就能看懂、修改、审阅。
2. **上下文缓存友好**：不做每轮自动注入；只在会话边界生成快照。
3. **AI 使用简单**：模型只需区分"记录过程"和"保存结论"。
4. **智能但保守**：支持去重、冲突检测、过期、确认状态和新旧关系，不擅自替用户合并事实。
5. **故障不阻塞会话**：文件损坏、索引损坏、统计损坏只能降级，不能让模型步骤失败。
6. **运行时轻量**：不依赖 embedding、向量库、SQLite 或 LLM 自动整理。

### 1.4 核心不变量

以下规则必须在设计和测试中保持不变：

- Markdown 日文件是长期记忆的真相源；日志 Markdown 是项目日志的真相源；
- `INDEX.md` 和 `.state/` 都是**可重建派生物**，不作为记忆内容的写入输入；唯一例外是 `INDEX.md` 头部的 `next-id` 注记参与编号水位线判定与重建（§6.1）；
- 长期记忆 ID 永久稳定，正常路径下永不复用（仅"水位线双丢失 + 历史最大编号条目已被人工删除"这一降级路径可复用，且必须告警，§6.1）；
- 日志不进入普通会话索引；
- 长期记忆只在**新会话**和**会话恢复**时注入（不含任何中途时机，§9.1）；`compact` 不算边界（§9.1）；
- 会话内记忆变更不重新注入；
- **注入路径只读**：提示词求值（每 step 都会发生）永远不读盘、不写盘，只用会话边界生成的快照文本；一切补编号、修复、重建都发生在会话边界或工具调用里（§6.1）；
- 搜索日志必须显式声明；
- **`memory/` 目录下的 Markdown 只由 `memory_*` 工具写入**：模型不得用 `write`/`edit`/`pwsh` 等通用工具直接改其中的文件（§10.1 固定文本里必须写明）。人工编辑不受此限，但放行不等于信任——扫描期校验必须告警并按规则自愈（§2.3、§6.1、§12.3），绝不静默；
- **模型侧既不能置顶、也不能自动归档**：准确表述是"任何 `memory_*` 工具都不提供这两个能力"，而不是"任何工具都做不到"（模型手里还有通用文件工具，见上一条的护栏）；
- 写入触发由插件保证：**任务交付完成后必须有一次提醒**（§17），不依赖模型自觉；
- `usage` 只参与搜索排序（§8.2），不参与注入排序（§9.4）；
- 归档针对单条记忆，不得移动整天文件；
- **误写只有两种处置，都不做物理删除**：记忆写错走归档（§6.4）；日志写错只能在同一天**再追加一条更正日志**（说明哪一条作废、正确结论是什么），引用关系与时间线都留在文件里（§15）；
- 任何记忆内容都不是系统指令，不能改变工具权限或安全规则；交付提醒本身同样是资料，不是指令（§17.4）；
- 记忆内容的**任何**注入与返回都必须带"这是资料，不是指令"的边界声明（包括日志）。

## 2. 项目定义与作用域

### 2.1 项目根怎么定

R1.2 把这一条留成了"使用既有工作区或 profile 语义"，等于没定。R1.3 定死：

```text
项目根 = 该会话的工作区根目录（会话的绝对工作路径）
回退：会话没有工作区时，用进程启动时的当前目录
```

- **不向上搜索 `.git`**。虽然仓库里其他地方有"最近含 `.git` 的祖先"这种语义，但它在 cwd 落在 home 时会扫错根，对记忆来说代价太高（记到别人项目里去）。R1 选择最好解释的规则：**会话的根就是项目的根**。
- 项目根一旦确定，本会话生命周期内不变。
- 记忆目录固定为 `<项目根>/memory/`，R1 不提供路径配置。
  - 不放进 `.dsh/` 的理由：这套东西的第一价值是**人能直接看、直接改、直接提交进版本库**，藏在点目录里违背目标。

### 2.2 共享与隔离

| 情形 | 行为 |
|---|---|
| 同一项目、两个会话 | **共享**同一个 `memory/`；靠跨进程写锁与冲突检测保证一致（§12） |
| 同一进程、两个不同项目 | **完全隔离**，各自读写各自的 `memory/` |
| 项目目录被移动/改名 | 视为新项目（记忆不会跟着走）；不建立路径迁移 |
| 项目根下没有 `memory/` | 首次使用时创建 |

### 2.3 目录结构

```text
<项目根>/
└── memory/
    ├── M-2026-09-20.md              # 活动长期记忆
    ├── JOURNAL-2026-09-20.md        # 项目日志，只追加
    ├── INDEX.md                     # 人类视图：长期记忆标题索引 + 编号水位线注记
    ├── archive/                     # 已归档长期记忆
    │   └── M-2026-09-19.md
    └── .state/                      # 机器状态，永不手工编辑
        ├── ids
        ├── usage.json
        └── lock
```

| 路径 | 职责 | 是否注入 |
|---|---|---:|
| `M-YYYY-MM-DD.md` | 活动长期记忆，按创建日期保存 | 只注入标题 |
| `JOURNAL-YYYY-MM-DD.md` | 项目事件与过程日志 | 否 |
| `INDEX.md` | 人类视图：**全部非归档条目**的标题索引 + 头部水位线注记 | 否（只作为人类视图） |
| `archive/M-YYYY-MM-DD.md` | 已归档长期记忆 | 否 |
| `.state/ids` | 编号水位线 | 否 |
| `.state/usage.json` | 长期记忆详情读取统计 | 否 |
| `.state/lock` | 跨进程写锁 | 否 |

**`INDEX.md` 的内容规则**（R1.2 完全没写，R1.3 补齐）：

- 列出全部**非归档**条目（含 `candidate`、`superseded`、派生 `expired`），每行形如 `[★ #0007] 约定 · 标题 · 状态 active`（状态用中文写法，与 §14.4 的"字段名全中文"一致）；
- `★` 只渲染在**参与注入**的置顶条目上；不参与注入的条目即使写了 `置顶：true`，也在行尾以 `（置顶）` 保留人工意图，不渲染 `★`；两个行尾标记同时出现时，顺序固定为 `（置顶）⚠ 超限未注入`；
- 头部固定一行 `next-id: 0011`，作为编号水位线的第二份记录（§6.1）；
- 手工超限、未进入注入的条目**仍要列出**，行尾标 `⚠ 超限未注入`（§5.6）；
- 归档条目不出现在 `INDEX.md`（它们在 `archive/` 里）；
- `INDEX.md` 是可重建派生物，不作为记忆内容的写入输入（头部 `next-id` 注记除外，§6.1）；人工可随意重排，重建时按下面的顺序重写；
- **重建顺序**：先列参与注入的置顶条目（按 §9.4 去掉首键的排序链），再按状态分组 `active → candidate → superseded → expired（派生）`，组内按 §9.4 排序链（首键 `置顶` 只对参与注入的条目有效，非注入条目按 `置顶 = false` 处理）、末位按编号升序；**已在前段列出的置顶条目不再在状态分组里重复列出**；
- **人工改动不作为输入，但必须被校验**：头部 `next-id` 与 `.state/ids`／实际最大编号不一致时，按 §6.1 取三者最大值修正并告警；行尾标记（`（置顶）`、`⚠ 超限未注入`）、中文状态写法属渲染产物，人工改错只影响人类视图，不参与任何判定——但**发现被改过就要在返回或告警里说一次**（§12.3），不静默覆盖。

### 2.4 不做的范围，以及跨项目事实该放哪

R1 不提供用户级记忆、全局记忆、跨项目记忆或共享 scope。同一条经验适用于两个项目时，用户需要在另一个项目里明确写一遍。

但这会引出一个真实问题：像"远端任务默认用 `ssh us`"这种事实本来就是跨项目的。R1 的立场是：

```text
真正的跨项目知识 → 放进技能、项目模板或团队文档，不要塞进某个项目的 memory/
只在一个项目内成立的结论 → 进该项目的 memory/
```

这条边界要写进固定提示词（§10.1），否则模型会把通用事实写进第一个碰到的项目里。

## 3. 长期记忆与项目日志的区别

### 3.1 长期记忆

回答：以后处理这个项目时，哪些稳定结论值得优先参考？

适合写入：

- 项目已确定的设计约定与默认方式；
- 已验证的配置、路径、端口和运行事实；
- 可重复执行的操作流程；
- 已确认的故障原因、反例和经验教训；
- 对未来任务有明显复用价值的结论。

不适合写入：

- 一次性聊天过程和单次命令输出；
- 尚未验证的猜测；
- 只对当前请求有用的临时上下文；
- 完整命令输出、大段日志粘贴；
- 密码、Token、Cookie、私钥等凭据。

### 3.2 项目日志

回答：这个项目过去发生过什么？当时做了什么？结果和证据是什么？

适合写入：

- 本次尝试了哪些方案、失败在哪；
- 某次修改的时间、结果与验证方式；
- 某个问题如何定位与解决；
- 尚未形成长期结论的过程信息；
- 以后可能需要追溯的上下文。

日志默认不参与普通注入、不参与长期记忆排序，也不会因为被搜索就提升优先级。日志不自动升级为长期记忆，需要模型或用户显式提炼。

### 3.3 判断规则

```text
只是记录发生过什么？         → memory_log
以后遇到类似任务应直接复用？   → memory_write
还不确定是否值得长期保留？     → memory_log（必要时另行写 candidate 记忆）
用户明确说"记住这个"？        → memory_write
跨项目通用的知识？            → 不进项目记忆（§2.4）
```

一次事件同时有过程和结论时，分别写：

1. `memory_log` 记录过程、证据和结果；
2. `memory_write` 保存验证过的长期结论；
3. 在长期记忆的 `详细` 或 `关联日志` 里指回日志。

## 4. 长期记忆的类型、状态与字段定位

### 4.1 四种类型

类型用于帮助人浏览、筛选、排序，并提示模型写出正确粒度。**类型以文件里的 H2 分节为准**（§5.1），不是靠标题文本猜。

| 内部值 | 展示名 | 记录什么 | 默认优先级 | **排序权重** |
|---|---|---|---|---|
| `convention` | 约定 | 项目确定采用的方案、默认方式、设计决策 | high | 1（最高） |
| `fact` | 事实 | 已确认的项目、环境、配置、行为事实 | medium | 2 |
| `procedure` | 流程 | 可重复执行的步骤与排障流程 | medium | 3 |
| `lesson` | 经验 | 踩坑、反例、限制、以后不要重犯的教训 | medium | 4 |

类型顺序固定为 `约定 > 事实 > 流程 > 经验`。理由是：约定是"照做就对"的东西，最该先被看到；经验虽然值钱，但通常只在特定场景触发。

> 偏好类内容的归属：**"偏好"按约定处理**（例如"这个项目回复保持简短"就是一个约定）。R1 不新增第五类。

### 4.2 状态

| 状态 | 含义 | 默认注入 | 谁来产生 |
|---|---|---:|---|
| `active` | 当前有效 | 是 | 默认值 |
| `candidate` | 尚未确认的候选结论 | 否 | `memory_write` 显式传入 |
| `superseded` | 已被新记忆取代 | 否 | `memory_write --supersedes`（§6.3） |
| `expired` | 已超过有效期 | 否 | **读取时按 `有效至` 派生**，不落盘 |
| `archived` | 已移入归档区 | 否 | `memory_archive` |

两条硬规则：

1. **`expired` 是派生状态，不是字段值。** 读取某条记忆时计算：`当前日期 > 有效至`（且 `有效至` 不是 `永久`）即视为 expired。这样避免"日期过了但状态字段还写着 active"的不一致。工具只允许写 `active` 和 `candidate`；`superseded` 只能由 `supersedes` 产生；`archived` 只能由归档产生。

   派生应用于**全部读取点**：会话边界注入、`memory_search` 的结果过滤、`memory_archive` 的恢复前置检查、`memory_edit` 的查重与冲突检查。`当前日期` 取**本机本地日期**，与日志条目的归属日期同一口径（§5.4），不使用 UTC。
2. **状态冲突时按固定优先序判定**，只呈现一个：

```text
archived > superseded > expired > candidate > active
```

即一条记忆既被取代又过了有效期，对外显示 `superseded`。

"候选事实"应写成 `类型：事实` + `状态：candidate`，不能把 `candidate` 伪装成一种类型。

### 4.3 优先级与置信度的定位

- **优先级**：主要给人看，同时是同一类型内的软排序键。它会**参与排序**，但排在类型之后（§9.4）。
- **置信度**：`confirmed / observed / inferred / temporary`，表示证据强度，参与排序，排在优先级之前，排序方向为 `confirmed > observed > inferred > temporary`。四档的分工判据如下（避免它和 `candidate`、`有效至` 三重表达同一件事）：

  | 值 | 用在什么时候 |
  |---|---|
  | `confirmed` | 用户确认过，或已实测复现 |
  | `observed` | 本次确实观察到，但只出现一次、未二次验证 |
  | `inferred` | 由现象推断得出，没有直接证据 |
  | `temporary` | 只会短时间成立的观察（配合一个短的 `有效至`） |

  分工原则：**"可能不算数"用 `candidate` 表达；"只有一段时间有效"用 `有效至` 表达；`temporary` 只用于两者同时具备的情况**，不等于 `candidate` 的同义词。

R1.3 相对 R1.2 的一处收敛：**排序不再同时使用"优先级 + 类型"两个近似重复的维度作主键**。主排序用类型，优先级只在其内部微调；这样排序结果更容易解释（不会出现"中优先级的经验排在高优先级事实之前"却看不出原因）。

### 4.4 样例对照

| 内容 | 类型 |
|---|---|
| 项目默认使用 `pnpm` 而不是 `npm` | 约定 |
| web profile 监听 3080 端口 | 事实 |
| 修改 patch 后如何执行配置验证 | 流程 |
| 依赖清单变化不会随 patch 热加载生效 | 经验 |
| 某次命令在今天失败了 | 日志，不是长期记忆 |
| 可能是 DNS 导致连接超时，但还没验证 | 日志；确需保留则 `事实 + candidate` |

## 5. Markdown 真相源格式

### 5.1 长期记忆文件

```markdown
# 记忆 · 2026-09-20

## 约定

- [#0007] 项目默认使用 SSH 别名 `us` 连接服务器
  - 状态：active
  - 置顶：true
  - 优先级：high
  - 置信度：confirmed
  - 创建：2026-09-20
  - 更新：2026-09-20
  - 标签：ssh, server
  - 别名：myserver, 服务器
  - 详细：详见本项目的部署文档第 3 节。

## 经验

- [#0008] DSH bundle 成员变化后必须重启 profile
  - 状态：active
  - 优先级：medium
  - 置信度：confirmed
  - 创建：2026-09-20
  - 更新：2026-09-20
  - 来源：实测
  - 关联日志：J-20260918-1542

```

标题行的职责统一定义为两件事：

```text
编号 + 可独立使用的完整陈述
```

**类型不写在标题行里**，由所属 H2 分节承载；索引渲染时再补上可读类型（§10.3）。R1.2 曾写"标题行承担编号 + 类型 + 陈述"，与实际格式不符，R1.3 统一为上面这种。

### 5.2 字段表

字段有两种摆放位置，语义不同：

- **标题行**：只有 `[#编号]` 和陈述文本；
- **缩进块**：所有机器字段与人类备注，一行一个，多行值用更深一级缩进续行（§5.5）。

| 字段 | 取值 | 说明 |
|---|---|---|
| `状态` | active / candidate / superseded / archived | `expired` 不写盘，见 §4.2 |
| `置顶` | true / false（可省略，默认 false） | **纯人工字段**，工具永不写入；参与注入时在 `INDEX.md` 与会话边界快照的 `[置顶记忆]` 段渲染为 `[★ #编号]` 前缀（§5.2 结论 2）；工具返回不渲染 `★` |
| `优先级` | high / medium / low | 缺省由类型推导 |
| `置信度` | confirmed / observed / inferred / temporary | 缺省 observed |
| `创建` | YYYY-MM-DD | 缺省取所在文件日期 |
| `更新` | YYYY-MM-DD | 缺省取所在文件日期 |
| `有效至` | YYYY-MM-DD 或 永久 | 缺省 永久 |
| `标签` | 逗号分隔 | |
| `别名` | 逗号分隔，供检索命中 | |
| `关联` | `#0001, #0002` | 相关记忆 |
| `取代` | `#0003` | 本条取代了谁 |
| `取代者` | `#0021` | 本条被谁取代（由 `supersedes` 自动写）；**只记录最后一个取代者**，完整取代链由各条自身的 `取代` 字段追溯，不做双向一致性强校验 |
| `关联日志` | `J-YYYYMMDD-HHMM` 或日期 | |
| `来源` | 用户确认 / 实测 / 文档 / 日志 或自由文本 | |
| `详细` | 文本，可多行 | 原因、边界、例外、验证结果 |
| `归档时间` | YYYY-MM-DD HH:MM | 只出现在 `状态：archived` 的条目上，由 `memory_archive` 写入 |
| `归档原因` | 文本 | 由 `memory_archive` 写入；恢复时移除 |
| `归档前状态` | active / candidate / superseded | 归档时保存原状态；恢复时回填并删除该字段（§6.2） |

关于 `置顶` 的四个明确结论：

1. 它是**人的意志**，不是模型的。工具不接受、也不会写入该字段；模型不能置顶（§1.4）。
2. `★` 只出现在两处：`INDEX.md` 中**参与注入**的条目行，以及会话边界快照 `[置顶记忆]` 段的条目行（§9.4：置顶条不再重复出现在 `[项目记忆索引]` 段）。渲染形如 `[★ #0007] 约定 · …`；`★` 是渲染产物，**不计入 160 字标题上限**。**工具返回（§10.4）一律不渲染 `★`**，只给 `[#0007]`。
3. 置顶条**不会因普通索引的截断而被省略**（§9.4）；置顶条自身超过 `maxPinnedItems` 时，按 §9.4 顺序省略尾部置顶条，并在说明行按 §9.4(a) 的固定文本报告（无省略时整句不出现）。
4. **置顶只对参与注入的条目生效**：`状态 active`、未过期、未归档的条目才计入 `maxPinnedItems` 并渲染 `★`；`candidate`、`superseded`、派生 `expired` 条目上的 `置顶：true` 不占名额、不渲染，但在文件与 `INDEX.md` 里原样保留；已归档条目的 `置顶：true` 只保留在归档文件里（归档条目不出现在 `INDEX.md`，§2.3）。

### 5.3 缺省值

缺失字段使用默认值：

```text
状态 = active
置顶 = false
优先级 = 类型默认值（约定=high，其余=medium）
置信度 = observed
创建 = 所在文件日期
更新 = 所在文件日期
有效至 = 永久
```

### 5.4 日志文件

```markdown

- 结果：确认插件只读写当前项目根目录下的 `memory/`。
- 决策：不提供用户级、全局级或跨项目记忆。
- 详细：移除 scope 字段，项目边界由会话工作区根决定。
- 后续：更新设计并补充提示词。
- 关联记忆：无

- 时间：2026-09-20 15:10
- 尝试：修改 profile patch 并执行配置检查。
- 结果：patch 修改可热加载；依赖清单变化仍需重启 profile。

- 关联记忆：#0008

> 当天这两条日志与 `J-20260918-1542` 讲的是同一件事：日志**允许同一事件多次出现**（§7.5），记忆 `#0008` 只关联其中一次。
```

- 日志条目 ID 为 `J-YYYYMMDD-HHMM`，同一分钟多条追加 `-2`、`-3`。
- **日志 ID 必须唯一**（R1.2 写的"尽量唯一"会让 `关联日志` 引用失准）。生成后若发现冲突则重发。
- 日志的最小必需字段是**标题和内容**；`时间`、`结果`、`决策`、`证据`、`后续`、`关联记忆`、`标签` 都可选。
- 日志不参与长期记忆编号分配。
- **日志条目的归属日期 = 写入时刻的本地日期**，与 `J-YYYYMMDD` 前缀、文件日期同源；`时间` 字段只作展示，检索（含 `dateFrom/dateTo`）一律按归属日期，不解析 `时间` 字段。

### 5.5 语法契约

这一节是解析的契约，R1.2 没写，也是人肉编辑最容易踩的地方。R1.3 只写了形状（缩进字段行、多行值、未知字段保留），**没有写判定规则**；R1.4 补上第 4、5、7、10 条的相对判定，否则"顶格字段行"与"忘了写编号的新条目"在解析上同形，会静默丢内容。

1. 条目 = 一行标题行 + 若干字段行（字段行的缩进可以缺失，见第 7 条）。
2. 标题行形如 `- [#0007] 文本`，`-` 或 `*` 都接受，编号缺失时按 §6.1 补发。
3. 字段行形如 `<缩进>字段名：值`，冒号可用中英文冒号（`：` 或 `:`）。
4. **缩进按相对深度判定，不按字符数比较**：比所在条目的标题行更深 = 字段行；比字段行再深 = 该字段的续行。Tab、全角空格（U+3000）、连续半角空格一律等价，只表示"更深一级"；渲染回写时统一为两个半角空格 × 深度。缩进出现跳跃（例如标题行下直接深两级）时，按"比上一行更深即为下一级"处理并记 warn。
5. **多行值**：续行属于上一字段，渲染回文件时保持相同缩进。`详细` 可以安全地包含多段文字，但**不应包含空行**——空行终止该条目：空行之后若仍是缩进行，按"人类备注"原样保留且不归属该条；若是顶格列表行，按第 2 条当作新条目。两种情况都要记 warn（"条目内含空行"）——**内容不丢、但要告警**。
   **工具侧必须当场拒绝含空行的 `详细`**（`invalid_param`，并给出改写建议）：不允许"先写进去再说"——落盘后再解析时后半段会变成孤儿行／未知字段，而且**每次 `memory_edit` 都会再累积一批残留**（实现阶段真机发现的缺陷：同一编号越改越脏）。首尾的空白行可被去掉后接受，**内部**空行一律拒绝。人工直接在文件里写空行仍然只告警、不拦截（人工路径没有"拒绝"这个动作，见 §12.3）。
   **同一条纪律适用于项目符号行**（交付后增补）：`详细` 的续行若以 `- `／`* ` 开头，会被解析成**条目字段**（第 3、6 条）或"**无法归类的行**"（`free-field`），落盘后**工具再也清不掉**（第 6 条要求原样回写），且**逐代累积**；工具侧同报 `invalid_param` + 改写建议（§7.1）。人工在文件里这样写仍只告警。
6. **未知字段**（不在 §5.2 表里的名字）一律按人类备注原样保留：解析时存下，回写时按原顺序写回。回写锚点规则：每个未知字段记录它**紧邻的前一个已知字段名**（若它位于该条目字段区最前，锚点记为"标题行"），回写时插在同一锚点之后，保持相对顺序。任何编辑都必须保证不丢未知字段、不重排已知字段之外的内容。
7. **顶格行（零缩进）的判定**：三条互斥规则，按顺序判——
   - 顶格且匹配已知字段名（`^字段名[：:]`）→ 视为当前条目的字段行，记 warn（"字段行缺少缩进"）；当前没有所属条目时按"游离字段"原样保留为备注并 warn；
   - 顶格且是列表项（`-` 或 `*` 开头）→ 视为一个新的条目，缺编号按 §6.1 补发；
   - 其余顶格行 → 视为人类备注，原样保留、不归属任何条目，记一次 warn。
8. **已知机器字段**重复时后者胜出并记 warn；**未知字段**重复时全部保留、按出现顺序原样回写，只是不参与解析（否则会违反第 6 条）。
9. 文件里的空行、分节标题的缺省、条目之间的顺序同属人类可读性的一部分，工具除归档/恢复外不主动整理。
10. **分节与条目的关系**：条目归属它上方最近的一个 H2 分节（§4.1）；出现在任何 H2 之前的条目记 warn，并在下一次写入该条时按类型归位到对应分节（内容不丢）。
11. 以上每一条"记 warn"都必须能在**工具返回或会话边界告警**中被看到（§12.3），不允许只写进日志文件。

### 5.6 长度上限与超限处置

| 对象 | 上限 | 工具写入超限 | 手工写入超限 |
|---|---|---|---|
| 标题 | 160 个 Unicode 字符（**建议 ≤60**） | 拒绝该条，整批不写入 | 告警 + 该条**不进入会话边界快照的索引段与注入** |
| 详细 | 8,000 个字符 | 拒绝该条，整批不写入 | 告警 + 该条不进入会话边界快照的索引段与注入 |
| 单条总计 | 8,600 个字符（标题上限 + 详细上限 + 字段开销的兜底值） | 拒绝 | 告警 + 不进会话边界快照的索引段 |

关键变化：手工超限的条目**不能被静默忽略**。只要一次注入里存在"未索引条目"，快照末尾必须出现一行统计（**文本由 §9.4 第 5 步统一定义**）：

```text
有 2 条长期记忆因超出长度上限未被索引，请修正其标题或详细。
```

否则用户会以为"我写进去了"，实际上它永远不会被模型看见——这是 R1.2 的一个隐形陷阱。

手工超限条目**仍然出现在 `INDEX.md`**（行尾标 `⚠ 超限未注入`），只有会话边界快照不列入——否则这条记录会从人类视图里彻底消失，等于把隐形陷阱从模型挪到了人身上。

## 6. 编号、归档与状态转换

### 6.1 长期记忆编号

编号形如 `#0001`，在**整个项目内唯一**（跨活动文件与归档文件），编辑、移动、改类型、改状态都不换号，且**正常路径下永不复用**（唯一的例外见本节的降级条款）。

- 水位线存放在两处：`.state/ids`（机器）与 `INDEX.md` 头部注记（人类可见）。
- 新编号 = `max(.state/ids, INDEX.md 注记, 所有活动 ID, 所有归档 ID) + 1`。
- 水位线丢失时按上式重建。若两处水位线**同时**丢失、且重建值小于历史已分配的最大值（例如用户手工删过条目），记 warn 并接受这一降级——R1 不追加大型历史记录。此时 §1.4 允许的**唯一复用路径**生效，工具返回必须显式告警。
- **重复编号修复**（手工复制粘贴导致）：按"活动文件（文件名日期升序）→ 归档文件（文件名日期升序）→ 同一文件内出现顺序"排序，第一个保留原编号，其余自动发新编号并记 warn，不自动合并正文。
- **手工新增的无编号条目**：**扫描时发现就补发编号并写回文件**，不等它被索引或被工具操作——否则"`INDEX.md` 中不允许无编号条目"守不住。

**扫描与写回时机（R1.4 补，它是"注入路径只读"能成立的前置条件）**：

- 需要读全部条目的动作只有三类：① 会话边界建快照；② 写入类工具（`memory_write`／`memory_edit`／`memory_archive`）执行前；③ 显式重建（`INDEX.md` 被删、水位线丢失、人工触发）。
- **补编号、重复编号修复、`.state/ids` 落盘只允许发生在这三类动作里。** `memory_search` 一律只读：发现问题只返回降级告警，不改文件。
- 会话边界发生写回时，告警必须同时走三条通道：插件日志 warn、会话日志事件 `memory/degraded`（`session.append`）、以及**下一次任意 `memory_*` 工具返回的 `warnings`**（§12.3）。
- **提示词求值（每 step 都会发生）永不读盘、永不写盘**：只返回会话边界生成的缓存字符串；求值里出现 IO 或异常都会污染整个上下文组装（§9.1、§12.3）。

### 6.2 归档与恢复

归档 `#0012`：

1. 从原活动日期文件移除该条；
2. 追加到 `memory/archive/M-原日期.md`，保留原编号、类型、创建日期与正文；
3. 写入 `状态：archived`、`归档前状态`（原状态，允许 active／candidate／superseded）、`归档时间`、`归档原因`；
4. 重建 `INDEX.md`；
5. 恢复时放回原日期文件：**把 `归档前状态` 回填到 `状态`，并删除 `归档前状态`／`归档时间`／`归档原因` 三个字段**，其余字段与全部未知字段一律不动。`归档前状态` 是 `superseded` 时照原样回填，恢复后该条依旧不进入注入与默认搜索。

规则：

- 归档**针对单条记忆**，不能把同一天的其他条目一起移动。
- 原日期文件不存在、**或该文件缺少对应类型的 H2 分节**时（例如该类型的条目此前全部被归档），恢复操作按 §4.1 的固定顺序新建分节，不报错。
- 恢复前检查（R1.4 把 R1.3 那句无定义的"原类型与置信度不可接受"改写为可判定式，共三项）：① 编号冲突——目标编号已存在于活动区；② 与活动记忆精确重复（按 §8.3 判据）；③ 归档条目自身字段不可容纳——`状态`／`归档前状态` 不在 `active｜candidate｜superseded` 内，或类型不在四类内，或置信度不在四档内，或编号形态不合法。命中①或②即拒绝恢复，不自动合并；命中③即拒绝并把原条目原样留在归档区（**不猜测、不修复**，返回中给出具体是哪一项不合格）。**"已过期（派生 expired）"不算冲突**：恢复后按派生规则处理，并在返回里附加提示"该条已过期，建议同时更新 `有效至`"。
- 归档／恢复／取代都是跨文件操作，落盘顺序、intent 记录与崩溃后的收敛规则见 §12.1（R1.4 写死的实现契约）。
- 日志 R1 不提供逐条归档与编辑；日志文件按日期保留。

### 6.3 新旧记忆关系

- **只修正措辞、补充细节** → `memory_edit`，保留原编号。
- **新事实取代旧事实** → 一次 `memory_write` 调用完成，不允许拆成两步：

```json
{
  "entries": [
    {
      "kind": "fact",
      "title": "web profile 监听 3180 端口",
      "detail": "端口从 3080 调整为 3180。",
      "supersedes": ["#0011"]
    }
  ]
}
```

一次调用的效果（全成或全败）：

1. 写入新编号条目；
2. 新条目写 `取代：#0011`；
3. `#0011` 写 `状态：superseded` 与 `取代者：#新ID`；
4. 旧条目正文**不修改**，保留可追溯；
5. 重建 `INDEX.md`（旧条目自动退出注入与默认搜索）。

三条补充规则：

- 同一批内任一编号最多被一条新条目取代；两条新条目指向同一旧编号 → 整批拒绝（`conflict`）；
- `supersedes` 只能指向**已存在**的编号，不能指向同批新条目（否则同批内会重新长出双活态）；
- 被取代条目若带 `置顶：true`，返回必须提示："#0011 原为置顶，已随取代退出注入；如需保留，请在人工编辑时把 `置顶：true` 移到 #新编号。"工具**不自动搬运**置顶标记（§5.2）。

R1.2 要求模型手动发两次调用，中途失败会出现"新条目已写、旧条目仍 active"的双活状态。R1.3 把它收进一次原子操作。

### 6.4 误写处置

设计上只有归档，没有物理删除：

```text
模型写错一条记忆 → memory_archive（archived 不出现在默认搜索与注入）
人工写错       → 直接改 Markdown，或归档
```

不提供 `memory_delete` 的理由：可追溯优先于整洁；归档已经拿到"看不见"的效果。

## 7. 工具契约

### 7.0 调用者权限与总则

R1.2 只在归档一节顺带提了一句"现有白名单"，权限模型没有定义。R1.3 明确到表：

| 工具 | 主 agent | 子代理 | 说明 |
|---|:--:|:--:|---|
| `memory_write` | ✅ | ❌ | 子代理的结论由主 agent 决定是否入库 |
| `memory_edit` | ✅ | ❌ | |
| `memory_archive` | ✅ | ❌ | |
| `memory_log` | ✅ | ❌ | 子代理过程由主 agent 汇总后记录 |
| `memory_search` | ✅ | ✅（**只读**） | 让子代理能查已有约定与踩坑记录，避免重复犯错 |

- 除 `memory_search` 外，所有记忆工具对子代理不可见。
- **"子代理"的判定口径（2026-09-26 补钉）**：只认正向特征——`header.origin === 'subagent'`，或 `delegationDepth > 0`（第三方 provider 可能不写 `origin`）。**`parentSession` 不能当判据**：宿主 **fork 顶层会话**时同样写它（`dsh-session` 的 `SessionStore.fork()`、`dsh-api-session-controller` 的 `commands.fork()` 都写 `meta = { cwd, parentSession: 源会话 id, isSeeded: true }`，没有 `origin`，`delegationDepth` 落盘时补 0），而真子代理由 `dsh-subagent` 的 `childSessionMeta()` 写 `origin: 'subagent'` + `delegationDepth ≥ 1`。误判的后果是四个写入类工具被 `restrict` 从可见面摘掉、模型一调用就拿到宿主的 `Error: unknown tool "<name>"`（`UNKNOWN_TOOL`）——这是 2026-09-26 的真机 P0。**fork 顶层会话按主会话处理**：登记白名单、建可写快照、可提醒；`parentSession` 有但形状不像 fork（`isSeeded` 不是明确的 `true`）的按"lineage 不明"隔离。
- **"不可见"的落地机制（R1.4 写死，R1.3 只声明了结果没给机制）**：宿主不会因为插件声明就按角色隐藏工具，真正的隐藏通道是 `tools.restrict(filter)`；它要求"作用域上下文"，因此在 `agent/created` 判定为子会话时，用**该子代理的上下文**（`agent.ctx`）调用 `restrict({ deny: [...四个写入类工具名] })`。三条硬约束：
  1. 必须在四个写入类工具**注册之后**调用——`restrict` 只接受当时已存在的全局工具名，名字未知会直接抛错；
  2. 只能用 `deny`，**不能用 `allow`**——`allow` 是"只保留这些"，会连带隐藏 `bash`／`read`／`write` 等其它全局工具，把子代理废掉；
  3. `execute` 层仍要查一次子代理判定与主会话白名单，作为第二道防线（子代理走非常规创建路径、或 restrict 未覆盖时兜底）——这一道沿用现有实现已验证的六道防线，不另造新机制。
- 子代理的 `memory_search` 同样受 `includeJournal` 与 `ids: ["J-..."]` 控制（仍然只读）；其正文读取计入 `usage`，但 `usage` **只影响搜索排序**（§8.2），不参与注入排序（§9.4），因此子代理的读取不会改变主会话下一次注入的内容。
- 所有工具都不接受 `scope` 参数：条目自动属于当前项目。
- 所有工具都不接受 `pinned`（§5.2）。
- 批量写、编辑、归档、恢复都是**全成或全败**（机制见 §12.1）。
- 任一工具的任何返回都不改变当前会话已注入的快照；要看新值必须主动查询（§9.1）。

### 7.1 `memory_write`

用途：写入可复用的长期记忆。

```json
{
  "entries": [
    {
      "kind": "lesson",
      "title": "DSH bundle 成员变化后必须重启 profile",
      "detail": "profile patch 支持热加载，但依赖清单变化不会随 patch 热加载。",
      "priority": "medium",
      "confidence": "confirmed",
      "status": "active",
      "tags": ["bundle", "restart"],
      "aliases": ["依赖清单", "热加载"],
      "source": "实测",
      "relatedJournal": ["J-20260918-1542"],
      "relatedMemory": ["#0007"],
      "supersedes": [],
      "expiresAt": null
    }
  ]
}
```

字段与规则：

- `kind` 必填，只能是 `convention / fact / procedure / lesson`；
- `title` 必填。**机械校验**：单行（不含换行符）、非空、≤160 Unicode 字符，违反即 `invalid_param`。R1.3 曾把"必须是一条完整陈述、不能是关键词堆或正文截断"列为**拒写条件**，但它不可机械判定、且 §7.6 也没有对应错误码——R1.4 把它降级为**写作要求**（写进工具 `description` 与固定提示词 §10.1／§10.2），不作拒写依据、不进 §14 验收；
- `detail` **不得包含空行**（§5.5 第 5 条）：命中即 `invalid_param`，并提示"空行会终止条目、让后半段残留成孤儿行并随编辑累积；需要分段请用中文分号／句号，或写成单行多句"。首尾空白行会被去掉后接受，内部空行一律拒绝。**`detail` 的续行也不允许以 `- `／`* ` 开头**（交付后增补）：这种行会被解析成条目字段或"无法归类的行"（`free-field`），落盘后**工具再也清不掉**（§5.5 第 6 条要求原样回写）且逐代累积；命中同报 `invalid_param`，提示改用中文分号／句号写在同一段里。`memory_edit` 的 `detail` 同此两条约束；
- `status` 只接受 `active`（默认）与 `candidate`；未验证的结论必须显式写 `candidate`；
- `priority` 通常不必填，缺省按类型推导；
- `expiresAt` 可填 `YYYY-MM-DD`，对应 `有效至`；不填即永久；**早于今天的取值一律拒绝**（`invalid_param`），返回文本："有效至不得早于今天；如需记录历史结论，请留空（永久）并在 `详细` 中说明"——否则会出现"写成功但立刻不可见"的静默隐藏；
- `supersedes` 见 §6.3，只接受**存在且未被归档**的编号：
  - 目标 `状态 active` → 正常取代；
  - 目标 `状态 candidate` → 允许，并一并标为 `superseded`；
  - 目标已是 `superseded` → 拒绝（`conflict`），返回该条现有的 `取代者` 编号，并提示模型改指向那个编号，避免把取代链压平；
  - 目标在 `archive/` 下 → 拒绝（`not_found`）；
- 不接受 `pinned`、不接受 `scope`；
- `title`、`detail`、`tags`、`aliases` 都执行敏感信息检测（§7.6）；
- 标题规范化后完全相同 → 整批拒绝并指出重复的编号；
- 标题高度相似 → 不拒绝，但在返回里附上候选编号与相似原因，由模型决定改写或另写；
- 同一主题但数值、版本、路径不同 → 不算**重复**（`duplicate`），但会命中冲突检测并返回冲突列表（`conflict`），由模型用 `supersedes` 处理新旧关系（例如 3080 与 3180）；
- 与活动记忆命中 §8.3 定义的**机械冲突** → 在返回里给出冲突列表与**可执行的下一步**，不写入该条。**R1.4 补的排除规则（没有它，§11 示例 D 的第二通调用会被同样的理由再拒一次，形成死锁）**：冲突判定范围**排除本批 `supersedes` 指向的编号**——带 `supersedes: ["#0011"]` 的写入不再与 `#0011` 判冲突。返回文本形如：`冲突：#0011（同主题 标签=port；端口 3180 ≠ 3080）。如需替换，请重发一次并带 supersedes:["#0011"]`。**语义相反的判定 R1 不做**（§8.3／§15），其余情形一律写入；
- 手工写入（人直接改 Markdown）的 `有效至` 早于今天**不拒绝**：按 §4.2 派生为 `expired` 并告警——工具路径能拒绝，人工路径只能派生（两处口径必须一致，否则"手工写进去就看不见"会变成静默陷阱）；
- 写入前完成整批校验，**任何一条失败则整批不写入**；
- 失败时返回必须**按 entry 序号逐条给出原因**（重复／冲突／超长／敏感／校验失败），否则模型只能盲猜、容易陷入重试循环。

### 7.2 `memory_edit`

用途：修改既有长期记忆，编号不变。

```json
{
  "edits": [
    {
      "id": "#0008",
      "detail": "补充新的验证边界。",
      "confidence": "confirmed",
      "tags": ["bundle", "restart", "热加载"],
      "expiresAt": null
    }
  ]
}
```

字段语义：

- 字段省略 = 不修改；
- `detail: null` = 清空详细；`tags: []` / `aliases: []` = 清空该字段；`expiresAt: null` = 改回永久；
- `expiresAt` **早于今天一律拒绝**（`invalid_param`），返回文本与 §7.1 相同："有效至不得早于今天；如需记录历史结论，请留空（永久）并在 `详细` 中说明"——否则可以把一条 active 记忆改成"昨天到期"，让它静默消失；
- `title: null`、`kind: null`、`status: null`、`id: null` 均非法（标题不能被清空；状态只允许改成 active/candidate）；
- **改 `kind` 必须同时把条目移动到目标类型的 H2 分节**（类型以分节为准，§4.1）；文件缺少目标分节时按 §4.1 的固定顺序新建。返回必须报告"已从「经验」分节移动到「事实」分节"。`kind` 变更不改编号、不改所在文件；
- **拒绝归档编号**：对 `archive/` 下的条目执行编辑返回 `not_found`，提示"#0012 已归档，请先用 `memory_archive` 的 `restore` 恢复再编辑"；
- 支持按编号批量；人工兜底允许按标题精确匹配，但多条命中必须拒绝并返回命中的编号列表；
- 修改标题、类型、状态、优先级、置信度后**重新执行查重与冲突检查**；
- 不改变 `创建` 日期，自动刷新 `更新` 日期；
- **未知字段必须原样保留**（§5.5 第 6 条）——编辑一次不能吃掉人工备注；
- 当前会话不重新注入；查看新值需调用 `memory_search`。

### 7.3 `memory_archive`

```json
{ "action": "archive", "ids": ["#0012"], "reason": "已被 #0018 取代" }
```

- `action` 只接受 `archive` 与 `restore`；
- `reason` 归档时建议填写，恢复时忽略；
- 恢复的前置检查见 §6.2，冲突即拒绝，不自动合并；
- 归档与恢复会影响多个文件（活动文件、归档文件、`INDEX.md`）：**进程存活期内必须整体成功或整体不动**；进程被杀时按 §12.1 的三条失败形态处理——允许出现"已生效子集"，但每个文件自身必须是语义完整的旧版或新版，且必须在下一个收敛点前收敛（§12.1）。

### 7.4 `memory_search`

用途：搜索长期记忆；在明确要求时搜索项目日志。

R1.2 的 `detail` 只出现示例值、没有正式枚举，`ids` 又只收长期记忆编号，导致"搜到日志却读不到全文"。R1.3 补齐：

**参数**

| 参数 | 取值 | 默认 | 说明 |
|---|---|---|---|
| `query` | 字符串数组 | — | 与 `ids` 二选一；数组内 AND 语义 |
| `ids` | 数组 | — | 与 `query` 二选一；`#0008` 取长期记忆，`J-20260920-1432` 取日志全文；**两种前缀不能混在同一次调用** |
| `kind` | 四类之一 | 全部 | 只搜长期记忆时有效 |
| `status` | active/candidate/superseded/all | active | `all` = 不按状态过滤（**已含 expired**）；只有 `active` 时才可用 `includeExpired` 追加过期条目 |
| `includeExpired` | bool | false | **只在 `status: active` 时有意义**：追加返回已过有效期的条目；`status: all` 已含 expired，此时本参数被忽略并进入 `warnings` |
| `includeArchived` | bool | false | 是否搜归档 |
| `includeJournal` | bool | false | 是否搜项目日志 |
| `dateFrom` / `dateTo` | YYYY-MM-DD | — | **仅对日志有效**：按日志文件日期过滤（对应"上周怎么解决的"这类提问） |
| `detail` | `titles` / `excerpts` / `full` | `titles` | 见下 |
| `limit` | 数字 | 10 | 超过 `limit` 时返回截断说明 |

**`detail` 三档的确切含义**

| 值 | 长期记忆返回 | 日志返回 |
|---|---|---|
| `titles` | 编号 + 类型 + 标题 + 状态/置信度 | 日志 ID + 日期 + 标题 |
| `excerpts` | 上一行 + `详细` 前 120 字 | 上一行 + 内容前 120 字 |
| `full` | 完整条目（含机器字段，`详细` 不截断） | 完整日志条目 |

**规则**

- `query` 与 `ids` 二选一，同时提供即报错；
- `query` 默认 AND；关键词匹配标题、详细、标签、别名，以及日志内容与标签；
- **默认只搜活动长期记忆**：`candidate`、`superseded`、`expired` 都不返回（可用 `status: all` / `includeExpired` 放开）；
- `ids` 里出现 `J-` 开头的编号时视为**显式日志访问**，自动等价于 `includeJournal=true`，不需要额外传参（否则 §10.4 的"按 J- 编号取全文"指引会因默认 `includeJournal=false` 而失效）；
- `includeJournal: false` 时，`query` 模式绝不触碰日志文件；
- **搜归档区必须同时满足两个条件（R1.4 交付后补正的口径）**：`includeArchived: true` **加上**放宽的 `status`（不能是默认的 `active`）。理由是 §4.2 里归档条目的状态是 `archived`，而 `status` 默认 `active`——两者**正交**（一个是"搜不搜归档区"，一个是"按状态过滤"），只给 `includeArchived` 会被状态过滤掉。`ids` 精确取详情**同样**受这两者约束（归档条目也要 `includeArchived: true` + `status: "all"`）；
- 当 `includeArchived: true` 而 `status` 仍为默认 `active` 时，工具**必须**在返回里说明真实原因（"归档条目会被状态过滤掉，请同时给 `status:'all'`"）并给出下一步，**不能**只回报"没有命中"——否则使用者会把"参数组合不对"误判成"归档区是空的"。同理，`ids` 未命中时的提示必须把两个条件都写全；
- **日志模式下**（`includeJournal=true`，或 `ids` 是 `J-` 编号）：`kind`／`status`／`includeExpired`／`includeArchived` 一律忽略，并在返回的 `warnings` 中列出；`dateFrom`／`dateTo` 只在日志模式下生效，长期记忆模式下给出即忽略并告警；
- 结果必须明确标注来源块：`[长期记忆]` 或 `[项目日志]`；
- 不因为命中数量少于某个阈值而隐式改变返回结构（保持可预期）；
- **只有返回长期记忆正文（`excerpts`/`full`）才计入 usage**；日志搜索不影响长期记忆排序；
- 命中日志并需要全文时，用返回的 `J-...` 再调一次 `ids: ["J-..."]`；
- `ids` 一次最多 10 条，避免整库灌进上下文。

### 7.5 `memory_log`

用途：记录项目过程。只追加，不进入长期记忆索引。

```json
{
  "entries": [
    {
      "title": "验证依赖热加载行为",
      "content": "改了 profile patch，patch 修改可热加载；依赖清单变化仍需重启 profile。",
      "result": "确认需要重启 profile",
      "tags": ["bundle", "restart"],
      "relatedMemoryIds": ["#0008"]
    }
  ]
}
```

- 自动追加到当天 `JOURNAL-YYYY-MM-DD.md`；自动生成 `J-YYYYMMDD-HHMM`，同分钟多条追加序号，并保证唯一；
- 不设置优先级、置顶、置信度，也不参与 usage；
- 不执行长期记忆查重：同一事件可以多次出现（过程本来就会重复尝试）；
- 仍执行敏感信息检测（§7.6）；
- 写入失败返回明确错误，但不能让当前模型步骤失败；
- 日志**不会**自动升级为长期记忆，必须另行 `memory_write`；
- `relatedMemoryIds` 只接受形如 `#0008` 的合法编号，引用不存在的编号时告警但写入（日志不该因为引用笔误丢内容）。

### 7.6 错误与敏感信息

**敏感信息策略**（R1.2 只有"执行检测"四个字，等于没定）：

| 项 | 规则 |
|---|---|
| 检测范围 | 标题、详细、标签、别名、日志标题与内容；不检测机器字段 |
| 命中类别 | 凭据类（密钥、Token、Cookie、会话票据、私钥、口令）、连接串类（含账号口令的 URL）、身份类（身份证号、完整手机号、银行卡号） |
| 处置 | **拒绝整批写入**，返回命中的 entry 序号 + 字段名 + 命中类别 |
| 回显 | **不回显命中原文**，只给位置与类别（避免把秘密写进会话上下文） |
| 误伤处理 | 返回中附一句"若确为无害的说明性文字（例如描述'如何配置 TOKEN 刷新流程'），请改写为不含具体值后再写入" |
| 日志 | 同规则，命中即拒绝该条 |

**统一错误码**

| 码 | 含义 | 模型应做什么 |
|---|---|---|
| `invalid_param` | 参数校验失败 | 按返回信息修正 |
| `not_found` | 编号不存在 | 用 `memory_search` 确认编号 |
| `duplicate` | 标题规范化后重复 | 改 `memory_edit` 或改标题 |
| `conflict` | 命中 §8.3 的机械冲突 | 决定编辑旧条、改写新条或用 `supersedes` 替代 |
| `sensitive` | 命中敏感信息 | 改写后重试 |
| `too_long` | 超长 | 拆条或精简 |
| `write_conflict` | 文件在写入过程中被外部改动 | 重读后重试（§12.2） |
| `locked` | 另一进程持锁且等待超时 | 稍后重试 |
| `degraded` | 部分文件损坏但仍完成操作 | 视返回的具体信息处理 |

返回给模型的文本永远包含三件事：**做了什么 / 结果如何（编号或原因）/ 下一步建议**。

## 8. 检索、去重与冲突

### 8.1 查询规范化

R1 只使用确定性的本地匹配：Unicode 规范化、中英文大小写归一、全角半角归一、路径分隔符 `/` 与 `\` 等价、单个关键词按不区分大小写的子串/词组匹配、关键词数组默认 AND。

### 8.2 排序（适用范围：`memory_search` 的返回顺序）

1. 编号精确匹配；
2. 标题精确或短语匹配；
3. 标签与别名匹配；
4. 标题命中次数；
5. 详细内容命中；
6. 类型权重（约定 > 事实 > 流程 > 经验）；
7. 状态（active 优先）；
8. 置信度（confirmed > observed > inferred > temporary）；
9. 优先级；
10. 最近使用（usage）的微小调整；仍平局时按 `创建` 日期新者优先；再平局按编号升序。

约束：usage 不能压过标题精确命中、`confirmed` 置信度或 `active` 状态。

> 注意：**这是搜索排序，与 §9.4 的注入排序是两套**。搜索要"最相关的先出现"，注入要"最重要的先出现且长期稳定"，用同一个公式会两头不讨好。R1.2 把两套并列却没说明用途，容易被读成矛盾。

### 8.3 去重与冲突

R1 不做模糊语义合并，只做保守判断：

- **精确重复**（规范化后完全相同）→ 拒绝写入（`duplicate`）；
- **高度相似** → 返回已有编号与**命中的是哪一条判据**，不自动覆盖，由模型决定改写或另写。界线必须可机械判定：规范化后一条是另一条的子串（方向无关），或两条标题的编辑距离 ≤ 较长标题长度的 20%（长度按 Unicode 字符数）；其余一律不提示；
- **冲突的机械判据（R1.4 把 R1.3 的"同一主题下数字/版本/路径/端口互不相容"拆成四要素，缺一不判冲突）**：
  1. **同一类型**：`kind` 必须相同——跨类型不判冲突（"端口 3080"是事实，"3080 端口的排障流程"是流程，二者不构成不相容）；
  2. **主题键命中**：两条的 `标签` 或 `别名`（规范化后）交集非空——主题由**人写的字段**确定，不由文本相似度猜；
  3. **数值指纹有差异**：从标题抽取的指纹集合不同。指纹包括端口号（`\d{2,5}` 且紧邻"端口"／`port`／`:`／`：`）、版本号（`v?\d+(\.\d+){1,}`）、路径（含 `/` 或 `\` 且至少两段）、独立数字串；
  4. **其余文本基本相同**：去掉指纹与主题词后，两条标题规范化后相同，或编辑距离 ≤ 较长者 20%。
  四条同时成立即判冲突（例：`[#0011] 事实 · web profile 使用 3080 端口` 与 `web profile 监听 3180 端口`，同 `kind`、标签交集含 `port`、指纹 `{3080}≠{3180}`、其余文本相同 → 冲突），命中后按 §7.1 处理（给冲突列表与下一步，且排除本批 `supersedes` 目标）；
- **语义相反的判定 R1 不做**（"必须重启"vs"不必重启"这类需要理解含义的冲突，见 §15）；无法机械判定的内容一律允许写入，必要时用 `candidate`；

取舍原则：误拒绝一条新事实的代价高于暂时保留两条待确认内容，所以冲突策略偏保守。

## 9. 注入策略与快照

### 9.1 注入时机（R1.3 收敛）

只在**会话边界**重建快照。宿主侧有三种到达方式（判定信号见下表），不带任何中途时机：

```text
1. 新会话创建（payload.source === 'startup'）
2. 会话恢复（payload.source === 'resume'：进程重启后继续，或从持久化历史重建）
3. 会话清空重开（payload.source === 'clear'）
```

**同一会话内的上下文压缩、截断续写不算会话边界**，也不重建快照——否则前缀稳定性会被最需要它的长会话破坏。

**宿主信号到边界的映射（R1.4 补：R1.3 只声明了两个时机，没说怎么从宿主那里认出来）**

宿主在 `agent/created` 事件的载荷里给出 `source`，取值域是 `'startup' | 'resume' | 'clear' | 'compact'`（当前只有 `'startup'`／`'resume'` 真的会被发出，另外两个是宿主预留值）。映射定死如下：

| `payload.source` | 是否边界 | 行为 |
|---|---|---|
| `'startup'` | 是（新会话） | 扫描 → 校验/自愈 → 建快照 → 落 `INDEX.md`；必要时建 `memory/` 与当天文件 |
| `'resume'` | 是（会话恢复） | 同上，按恢复那一刻的文件状态重建 |
| `'clear'` | 是（视为新会话） | 先清空该会话的旧快照缓存，再按新会话处理 |
| `'compact'` | **否** | 沿用已有快照，**不重建**；即使宿主将来开始为压缩发出该事件，也按本条执行（§9.1 的取舍是刻意保留前缀稳定，不是"因为现在没人发所以不管"） |
| 其它取值／未知／缺失 | 否 | 该会话尚无快照时按"新会话"兜底**一次**并记 warn；已有快照则不动 |
| **fork 顶层会话**（`parentSession` 有、`origin` 缺省、`delegationDepth` 0、`isSeeded: true`） | 是（同新会话） | 同 `'startup'`；宿主 fork 走 `ctx.agents.create()` → `dsh-agent-loop` 的 `publish("startup")`，实际拿到的 `source` 就是 `'startup'`，因此**不需要**额外的 source 分支；关键是它**不是**子会话（§7.0 判定口径） |
| 判定为子会话 | 建**只读**快照（不写盘） | 注入该只读快照（与主会话逐字同构）、应用 §7.0 的工具可见性限制（`restrict`）；不提醒 |

边界动作是一次性 IO（扫描 → 校验与自愈 → 建快照 → 重写 `INDEX.md`），完成后快照文本进缓存；**随后每次提示词求值只读缓存**（§6.1）。

两条删除项：

- **删除 R1.2 的"跨过本地日界后重新注入"**。它与"会话内记忆变更不重新注入"直接矛盾，而且跨午夜的会话正好是最需要保持前缀稳定的场景。日界只影响**新写入的记忆落到哪个文件**，不影响注入。
- **删除"会话重新打开"与"会话恢复"的措辞分叉**。R1.3 只承认一种：会话被重新组装上下文时算一次边界。

恢复时的行为定死：**按恢复那一刻的文件状态重建快照**。理由：恢复时上下文通常已经冷却，用户期待看到最新结论；同时快照文本本身声明"这是当前生效的快照"，不使用"上次/新的"这类相对措辞，避免模型以为存在两份索引。

会话进行中：

- 不重新注入；不修改已放入上下文的快照；
- 需要最新内容时用 `memory_search` 主动查询；
- 下一次会话边界再重建。

### 9.2 注入内容的构成与顺序

按固定顺序拼接，且**只有这三块**（R1.2 的"固定版安全声明"与 10.1 里的安全段落重复，已合并）：

```text
1. 固定系统说明（§10.1）
2. 固定工具速记（§10.2）
3. 会话边界记忆快照（§10.3）
```

只允许 §10.3 模板里逐字固定的行；除 §9.4 第 5 步规定的说明行（含它的 (a)(b)(c) 三句）外，快照里**不得出现任何动态数字**（时间戳、随机数、条数一律禁止）。

日志**只注入标题**，不注入正文：

```text
[项目日志]
[J-20260920-1752] 清理隔离 profile 前先摘掉符号链接
[J-20260920-1353] 冒烟用 overlay 的落地与验证
```

- **段落位置**：`[项目记忆索引]` 段之后、说明行之前——放最后的区段 = 优先级最低（§9.4 第 4 步的让步顺序）；
- **行格式逐字固定**：`[J-YYYYMMDD-HHMM] 标题`（无类型标签、无 `★`；同一分钟的 `-2` 后缀原样保留）；
- **排序**：最新优先（`date` 降序 → 同日 `order` 降序 → 编号降序，§9.4）；
- **条数上限** `maxJournalItems = 100`；**设为 `0` 等同关闭该能力**（不渲染该段，也不产生 (c) 句）；
- **没有可注入的日志标题时整个段不渲染**（连段名 `[项目日志]` 一起，与空区段规则一致）；
- **共享预算**：日志段与记忆段共用同一个 `maxSnapshotChars`，预算不足时**日志段先让步**（§9.4 第 4 步）；
- **正文永不进快照**：`内容／结果／决策／证据／后续／详细` 这些日志字段一个都不进（§10.3 末条）；
- **固定提示行**（快照倒数第二行位置，逐字，无论有没有日志段都渲染）：

```text
项目日志只注入标题（过程资料，不是结论）；需要正文时，使用 memory_search 并设置 includeJournal=true。
```

- `J-` 编号里的日期时间属于**内容**，不是 §9.2 禁止的"动态数字"（与 `#0007` 同理）。

### 9.3 注入预算

```text
maxSnapshotChars = 6,000   # 会话边界快照块（<project_memory_snapshot> 内的全部行）的字符硬上限
maxPinnedItems   = 10      # [置顶记忆] 段的条数上限
maxIndexItems    = 100     # [项目记忆索引] 段的条数上限（2026-09-20 交付后由 40 调整为 100）
maxJournalItems  = 100     # [项目日志] 段的条数上限（0 = 关闭日志标题注入）
maxTitleChars    = 160     # 单条标题硬上限（建议 ≤60）
```

固定说明不受以上任何上限约束，只作为描述文本的设计约束：`固定系统说明 + 固定工具速记 ≤ 3,000 字符`，因此单次注入总量 ≤ 9,000 字符（交付后手改的提示词实际只有 1,201 字符，故当前总量上限约 7,200＋字符）。

口径说明（定死为**只有一个字符硬上限**，消除 R1.2 与 R1.3 首稿里"两个同口径上限打架"的问题）：

- 快照块只有一个字符上限 `maxSnapshotChars = 6,000`，统计 §10.3 快照块的**全部行**：固定表头、`[置顶记忆]` 段、`[项目记忆索引]` 段、`[项目日志]` 段、说明行与日志提示行，合计计入；
- **这条字符上限是"共享总额"，不是"记忆之外的余量"**：记忆索引行、置顶行、日志标题行、表头与说明行**共用同一个 6,000**——抬高某个段的条数上限**不会**多出字符预算（只有 §10.1／§10.2 的固定说明与工具速记在 6,000 之外）。所以"索引段最多 100 条"与"快照 6,000 字符"是**两个独立约束，取先到者**；
- **三个**条数上限各自只管自己的段（`maxPinnedItems` 管置顶段、`maxIndexItems` 管索引段、`maxJournalItems` 管日志段）；
- 三个条数上限合计最多 10 + 100 + 100 = 210 行，按每行最长 160 字、加前缀（`[#0008] 经验 · ` 约 13 字符）计 ≈ 36,330 字符 ≫ 6,000，所以**实践中先撞到的是字符上限**，条数上限只是兜底；
  - 换句话说：索引段要真放满 100 条，标题得短到平均 ≈48 字以内（6,000 减去表头约 207 与日志段占用，再除以每行 ≈13 + 标题长度）；标题越长，实际进注入的条数越少，**这也是"标题建议 ≤60 字"的实际价值**；
- **段的优先级固定为 置顶 > 索引 > 日志**：预算不足时先省日志段，日志段省空后仍不足才回头省索引段（§9.4 第 3、4 步）；
- 因此给出软约束：**标题建议 ≤60 字**，写成一条能独立看懂的短陈述，长解释放 `详细`；
- 一条记忆若已进入 `[置顶记忆]` 段，**不再重复出现在** `[项目记忆索引]` 段（两段互斥）。

### 9.4 确定性、排序与截断

同一批文件在没有内容变化时必须产生完全相同的注入文本。注入排序：

```text
置顶 > 类型(约定>事实>流程>经验) > 置信度(confirmed>observed>inferred>temporary) > 优先级 > 创建日期 > 编号
```

- 这条链用于**普通索引段**；`[置顶记忆]` 段内部用同一条链，但**省略首项"置顶"**（否则自指）；
- **日志段用一条独立的链**（日志没有 `kind`／`confidence`／`priority`／`pinned` 字段，套不上上面那条）：

```text
创建日期(新者优先) > 同日 order(新者优先) > 编号(降序)
```

  即"**最新优先**"：越新的日志标题越靠前；同日同 `order` 的极端情况按 `J-` 编号**降序**收尾，保证同一批文件可复现；
- **日志标题不设单独的长度上限**（有意为之：§7.5 没有给日志标题定长度上限，在此另立一套会造出第二个长度体系）。日志段里每一条都**整条包含或整条省略**，与记忆条目同规则；
- **R1.4 从注入链里移除了"最近使用"**（R1.3 把它排在优先级之后）：`usage` 会随任何一次正文读取而变化（含子代理的读取，§7.0），留在注入链里会让注入顺序随"读行为"缓慢漂移，与"注入要长期稳定"（§1.3 第 2 条）直接冲突，也让 §14.35 的逐字符一致失去意义。`usage` 只保留在**搜索排序**（§8.2 第 10 键）里；
- 索引构建不随机采样、不依赖文件系统返回顺序；
- **术语定死：`省略` = 不进快照；`移除` = 从文件里删掉。** 截断只做前者，永远不做后者。

**截断算法**（R1.2 缺失）：

1. 先放 `[置顶记忆]` 段：按（省略首项的）排序链取前 `maxPinnedItems` 条；置顶条**不因普通索引的截断而被省略**，只有自身超过 `maxPinnedItems` 时才从尾部省略；
2. 再放 `[项目记忆索引]` 段：按排序链依次放入，每放入一条检查**本段条数**（≤ `maxIndexItems`）与**快照块合计字符数**（≤ `maxSnapshotChars`）；
3. 最后放 `[项目日志]` 段：按"最新优先"链依次放入，每放入一条检查**本段条数**（≤ `maxJournalItems`）与**快照块合计字符数**；`maxJournalItems = 0` 时本步整段跳过（也不产生 (c) 句）；
4. **让步顺序固定为 置顶（不可省）→ 索引段 → 日志段**：预算不足时**先**从日志段尾部（= 最旧的日志标题）整条省略，日志段省空后**再**从索引段尾部整条省略；触发任一上限时一律**从该段自己的排序尾部整条省略**，绝不把一条标题截成半句；
5. 末尾追加**一行**说明；它按需由**三句**固定文本组成，用句号分隔、只替换数字：

   (a) 发生省略或存在被省略的置顶条时写（**R1.4 定死三个数字的口径**，否则同一状态会产出不同数字，§14.35 在"有省略且存在置顶"时不可复现）：

```text
本次快照按排序省略了 N 条记忆；置顶记忆共 M 条，展示其中前 K 条。
```

   - `N` = 索引段被省略的条数 **+** 置顶段被省略的条数（即**全部被省略的参与注入条目**，置顶条也算在内）；
   - `M` = 参与注入的置顶条**总数**（含因超 `maxPinnedItems` 被省略的那些）；
   - `K` = `min(M, maxPinnedItems)`，即实际渲染出 `★` 的行数；
   - 三个数字都是 Unicode 字符无关的整数计数，直接替换文本里的占位字母。

   (b) 存在超限未索引条目时写（文本与 §5.6 一致）：

```text
有 N 条长期记忆因超出长度上限未被索引，请修正其标题或详细。
```

   (c) 日志段存在省略时写（`maxJournalItems = 0` 时永不出现）：

```text
另有 X 条日志标题未注入。
```

   - `X` = **可注入的日志标题总数 − 实际渲染条数**（可注入 = `id` 与 `title` 均非空的日志条目）；
   - 句子里**不写原因**：省略可能同时来自"条数上限"与"字符预算"，写明反而会给出半截事实；
   - 日志段的省略**绝不并进 (a) 句的 `N`**：`N` 的语义保持"被省略的参与注入长期记忆条数"不变（§14.44 的口径因此无需改动）。

   三句都不适用时整行不出现；适用时整行计入 `maxSnapshotChars`。

6. 说明行**必须保留**，并计入 `maxSnapshotChars`；若加入它后超限，按第 4 步的让步顺序继续省略（先日志段尾部、再索引段尾部）直至达标。

**空区段渲染规则**（R1.2 未定义，影响确定性）：

- 没有置顶记忆时，整个 `[置顶记忆]` 段**不渲染**（连标题一起省略）；
- 索引为空时保留 `[项目记忆索引]` 段并写一行 `（暂无长期记忆）`；
- 没有可注入的日志标题时，整个 `[项目日志]` 段**不渲染**（连段名一起省略；含 `maxJournalItems = 0` 的"功能关闭"情形）；
- 各段之间的分隔、标签拼写、换行位置在所有会话中完全一致；
- **确定性的比较对象**：全部 `M-` 活动记忆文件 + 全部 `JOURNAL-` 文件 + `INDEX.md` 三者内容一致时，必须产出逐字符相同的快照（§14.35）。**R1.4 把 `.state/usage.json` 从比较集里去掉**：它已经不参与注入排序（见上），把它列进来只会造成"usage 变了算不算文件没变"的歧义；`.state/ids` 同理不参与（它只影响新编号分配，不影响快照文本）。

## 10. 提示词设计

分四层：A 固定系统说明（长期不变）、B 固定工具速记、C 会话边界快照、D 工具返回内容。A、B **在每个角色内逐字固定**（主 agent 与子代理各一套，见下；角色之间不得混用）；C 只在会话边界变化；D 由工具调用自然进入上下文，不写回系统提示。

**再加一条独立通道 E：交付提醒（§17）**。它不是系统提示词的一部分，也不是工具返回，而是会话内通过 `steer` 投递的**一次性消息**：不改 A/B/C，不写回系统提示，也不刷新快照。把它单列，是为了让"注入了什么"这个问题在文档里有唯一答案——系统提示只有 A/B/C，D 在工具返回里，E 在会话消息里。

## 11. 提示词中的决策示例

### 示例 A／C：记住一个约定、以及尚未验证的观察（与 §10.1 同规则，只列判据）

- 用户说"以后这个项目都用 pnpm" → `memory_write`，`kind=convention`、`confidence=confirmed`；已有相似约定则改用 `memory_edit`，不新增重复条目。
- 模型自己发现"像缓存没刷新，但没验证" → `memory_log` 记录观察；确需保留则写 `kind=fact, status=candidate`，候选不进入注入。

### 示例 B：只记录一次操作过程

用户："我刚刚试了三个配置，第三个成功了，把过程记一下。"

模型行为：`memory_log` 写入尝试、结果与证据；不把三个配置都写成长期记忆；如果第三个方案已证明可复用，另行写一条 `procedure` 或 `fact`，并在 `关联日志` 指回本次日志。

### 示例 D：新配置替代旧配置

旧记忆 `[#0011] 事实 · web profile 使用 3080 端口`，验证后改成 3180。

模型行为：一次 `memory_write`，带 `supersedes: ["#0011"]`；系统自动把 `#0011` 标为 `superseded` 并写 `取代者`；不覆盖旧正文；必要时补一条日志说明变更原因。

### 示例 E：只想查历史过程

用户："上次我们是怎么解决这个 504 的？"

模型行为：`memory_search(query=[...], includeJournal=true, detail="excerpts")`；先给日志摘要；发现已提炼的长期经验则按编号取详情；查日志不改变长期记忆排序。

### 示例 F：跨午夜的长会话

会话从 23:50 持续到次日 00:20，期间写入了新记忆。

模型行为：注入的快照**不刷新**（§9.1）；模型如果要在当前轮使用新记忆，必须 `memory_search`；新记忆按真实日期落到次日的 `M-` 文件里。

### 示例 G：用户要求删掉一条记忆

用户："把那条写错的端口记忘掉。"

模型行为：`memory_archive`（不是删除），reason 写"内容有误"；说明它仍然可追溯、可恢复。若用户坚持要彻底删除，提示他直接编辑 Markdown 文件。

### 示例 H：候选转确认

`[#0013] 事实 · 疑似 DNS 导致连接超时（candidate）`，之后实测确认。

模型行为：`memory_edit` 把 `status` 改为 `active`、`confidence` 改为 `confirmed`，编号不变；下一次会话它才会出现在注入索引里。

## 12. 一致性、冲突与降级（语义要求）

本节只规定**必须成立的行为**，不规定做法。

### 12.1 写入的原子性

- 长期记忆的批量写、编辑、归档、恢复都是**全成或全败**：任何一条失败，所有条目保持原样；
- 日志追加是单条追加，失败即失败，不产生半条内容；
- 写入过程中若被其他进程/人改动，必须以"最终文件里看不出半个操作"为准；
- 归档与恢复跨多个文件，必须整体成立。

**实现契约（R1.4 写死机制）**：R1.3 把"多文件如何获得可恢复的中间状态"判为"不在本文档范围内"，但 §14.40 又要求验收它——结果是没有人负责。R1.4 明确如下，作为唯一允许的实现方式：

单文件写入：

1. **同目录临时文件 + `rename` 原子替换**（进程中途退出不会留半截文件；本条沿用现有实现已验证的做法）；
2. 写前比对文件指纹，或直接用宿主文件服务写入（两者都要能发现"文件被人工改过"）→ 发现即放弃旧快照上的修改、重读、重新校验（§12.2）。

多文件操作（归档／恢复／取代／`INDEX.md` 重建）：

1. 先在 `.state/` 落一份 `intent.json`：操作类型、涉及的目标文件清单、各文件的临时文件名、以及**回滚所需的原内容副本**；
2. 按**固定顺序**落盘：**先数据文件（`M-*.md`／`archive/M-*.md`、`JOURNAL-*.md`），再 `INDEX.md`，最后 `.state/ids`**——中间态永远可以由"数据文件 + 重跑一次重建"收敛，不会出现"索引说有、文件里没有"；
3. 全部完成后删除 `intent.json`：**删除 `intent.json` 就是提交点**；
4. **收敛点**：任何进程在下一次"会话边界扫描"或"写入类工具执行"开始前，若发现残留 `intent.json`，按它前滚（临时文件仍在就继续完成）或回滚（临时文件已丢就还原原内容副本），然后删除并记 warn，且必须把这件事带进工具返回的 `warnings`（§12.3）。

**允许的失败形态（R1.4 从"两种"改定为三条，并把崩溃场景纳入）**：

1. 进程存活期内任何失败 → **必须回到原样**：单文件写入尚未 `rename` 时天然成立；**多文件操作只要已经 `rename` 过任何一个文件，就必须靠 `intent.json` 回滚**（"已经开始 rename、但进程还活着"正是 intent 存在的第一个理由，不是只有崩溃才需要它）；
2. 进程被杀 → 允许出现"已生效子集"，但**每个文件自身必须是语义完整的旧版或新版**（绝不出现半条、半字段），且在下一个收敛点前被前滚或回滚；
3. 连收敛都做不到（例如 `intent.json` 本身损坏）→ 返回 `degraded`，把磁盘现状与 intent 路径一并报出，**绝不静默覆盖**。

对应验收：§14.40、§14.66。

### 12.2 与人工编辑共存

- 写入前发现文件被改动 → 放弃旧快照上的修改，重读、重新校验，自动重试**最多两次**；
- 两次之后仍然冲突 → 返回 `write_conflict`，**绝不覆盖用户的修改**；
- R1 不实现三方合并。

### 12.3 降级的边界

| 场景 | 行为 |
|---|---|
| 单个长期记忆文件损坏 | 跳过该文件，告警，会话继续 |
| 单条记忆格式损坏 | 跳过该条，**保留原文**，告警 |
| 日志文件损坏 | 跳过损坏日志，其余日志与记忆可用 |
| `INDEX.md` 损坏或落后 | 从活动记忆重建 |
| `.state/ids` 丢失 | 扫描活动与归档编号重建（§6.1） |
| `usage.json` 损坏 | 清空 usage，不影响搜索与注入 |
| 残留 `intent.json`（上次写入被杀） | 按 §12.1 前滚或回滚后删除，告警进工具返回的 `warnings` |
| 记忆／日志文件被通用工具（write／edit／pwsh）改过 | 扫描期校验：告警（指名是哪一条、什么问题），并按 §5.6／§6.1／§9.4 的规则自愈；**既不静默接受、也不静默覆盖**（§1.4） |
| 会话中途快照缓存缺失（异常导致） | 本会话内**不重建**（§9.1 不变量优先），返回里提示模型用 `memory_search` 取现值；下一次会话边界再重建 |
| 写入中途状态不确定 | 保留原文件，告警，不静默覆盖 |
| 日志写入失败 | 明确返回失败，不让当前模型步骤失败 |

降级时的告警必须**出现在工具返回里**（模型可见），而不是只写进日志文件；否则"缺失的记忆"会变成隐形错误。

## 13. 落地顺序

**阶段 0 · 格式、提示词与实现契约冻结**
确认项目根绑定规则（§2.1）、文件命名、四类类型与类型顺序、状态派生规则、固定提示词与工具速记；**同时冻结三处实现契约**——§12.1 的 intent 与落盘顺序、§6.1 的扫描与写回时机、§7.0 的 `restrict` 机制（R1.4 已把它们写进文档，不再留给实现者临场决定）；为现有实现建立备份。

**阶段 1 · 解析与数据模型**
按天解析长期记忆与日志；编号补发与重复修复；未知字段保留；损坏隔离；状态派生与取代关系；**§5.5 的六类人工编辑判定**（顶格字段行、缩进归一、续行内含空行、未知字段回写锚点、游离字段、H2 前条目）。

**阶段 2 · 五个工具**
先实现 `memory_log`（验证"只追加"最纯粹）；再 `memory_write`（含 supersedes 原子替换）；再 `memory_edit`、`memory_archive`、`memory_search`（长期记忆 + 日志双模式 + 日期过滤）。同步完成参数校验、敏感信息策略、逐条错误返回，以及**按 scope 的工具可见性**（§7.0：注册完成后再对子会话 `restrict({ deny })`）。

**阶段 3 · 索引与注入**
生成 `INDEX.md`；只在会话边界生成快照；接入固定提示词；实现条数/字符/置顶预算与截断算法；**接入 §9.1 的 `source` 映射**（`startup`/`resume`/`clear` 是边界、`compact` 不是）；验证"会话内不重新注入"与确定性排序。

**阶段 3.5 · 写入触发（§17）**
实现交付态状态机与提醒通道：`deliverables/presented` → `agent/turn-stopping` → `steer`，含消息形状校验、同轮消费、冷却放弃、abort 跳过、子代理隔离。**建议直接移植现有实现的交付态逻辑**（纯逻辑 + 16 条已按真实事件形状驱动的用例），只在提醒文案与工具名上适配新设计。

**阶段 4 · 智能行为**
精确查重、相似提示、冲突检测（§8.3 四要素）、candidate/superseded/expired 生命周期、关联日志与取代关系、usage 统计口径（只作用于搜索排序）。

**阶段 5 · 并发与崩溃收敛**
跨进程锁、人工编辑冲突重试、§12.1 的多文件 intent 与崩溃前滚/回滚、写入中断后的安全处置。

**阶段 6 · 真实环境验收**
新会话注入冒烟、恢复会话注入冒烟、工具真实调用、日志与记忆的检索边界、前缀稳定性、子代理权限（只读可用、写入不可见）、**交付提醒冒烟（交付轮提醒一次、纯问答零提醒、冷却命中放弃且不补发）**、**手工越权编辑与 intent 崩溃各注入一次**。

## 14. 验收标准

### 项目与文件

1. 项目根等于会话工作区根；无工作区时回退到启动目录；
2. 项目目录下只有该项目的 `memory/`，不存在用户级/全局扫描；
3. 同一项目多会话共享同一记忆库；不同项目互不可见；
4. 任一 `M-`／`JOURNAL-` 文件在无插件时可由人读懂：标题行含编号 + 完整陈述，字段名全中文，正文流里不出现内部机器 ID；
5. 标题行匹配 `^[-*]\s\[#\d{4}\]\s\S`，且其正文部分**不以 §5.2 表中任一已知字段名 + `：`／`:` 开头**，全部机器字段位于其后（R1.4 把这句机械化，替换 R1.3 的"行内不含任何 `字段名：值` 子串"——后者会误伤"别名：us"这类正常标题文本）；
6. 手工增加的未知字段在解析、编辑、归档、恢复后都不丢失；
7. 扫描时发现的无编号条目立即补发编号（不等到被索引，§6.1）；
8. 编号在正常路径下永不复用；降级路径（水位线双丢失 + 历史最大编号条目已被人工删除）会复用并必须告警（§14.53）；重复编号被自动修复且记 warn。

### 长期记忆行为

9. 四种类型能正确写入，类型以 H2 分节为准；
10. `candidate` 不进入注入；
11. `confirmed` 事实可按编号取完整详情；
12. 一次 `memory_write`（带 supersedes）能原子完成新旧替换，中途不产生双活状态；
13. 精确重复被拒绝，返回重复编号；
14. 相似但不确定的内容不会被静默覆盖，返回候选列表；
15. 归档单条记忆不影响同一天其他条目；
16. 归档记忆可恢复；原日期文件不存在、或该文件缺少对应类型的 H2 分节时，都能按 §4.1 的顺序新建分节并正确落位；
17. `有效至` 到期后该条自动不进入注入与默认搜索（派生 expired）；
18. 状态冲突按 `archived > superseded > expired > candidate > active` 呈现。

### 置顶

19. **四个写入类工具**（`memory_write`／`memory_edit`／`memory_archive`／`memory_log`）都不接受、也不写入 `置顶` 字段——这就是"模型无法置顶"的确切含义（R1.4 收窄 R1.3 的"任何工具都无法置顶"：模型手里的通用文件工具确实能改文件，那由 §10.1 的禁令 + 扫描期校验约束，不能靠工具能力来保证）；
20. 人工写的 `置顶：true`：**参与注入**的条目在 `INDEX.md` 与会话边界快照中都渲染为 `[★ #0007]` 前缀；**不参与注入**的条目（candidate／superseded／派生 expired）在 `INDEX.md` 行尾渲染 `（置顶）`、不出现 `★`；**已归档条目不出现在 `INDEX.md`**，其 `置顶：true` 只保留在归档文件里（§2.3）；两种渲染都不改变标题文本、都不计入 160 字上限。**新增的**置顶标记（在上一次索引之后新出现）——**R1.4 复核后的裁定**：文件层分不出写它的是人还是模型用通用文件工具，所以规则是 ① 它照 §5.2 结论 4 **正常生效**（人的意图优先，插件不擅自撤销；渲染规则与本节前三句完全一致）；② 只要它是新出现的，就必须在下次扫描**告警**并说明"本插件的工具从不写置顶"（§14.64），由人判断是否保留——**不**把"不生效于注入"当作护栏（那会撤销人的合法意图，且无法与模型越权区分）；
21. 置顶条不因普通索引的截断而被省略；置顶条数超过 `maxPinnedItems` 时，超出部分被省略并在说明行报告（数字口径见 §9.4 第 5 步 (a)）。

### 日志行为

22. `memory_log` 只追加当天日志；
23. 日志 ID 唯一，同分钟多条能正确加序号；
24. 日志不进入 `INDEX.md`、不进入会话边界快照；
25. `includeJournal=false` 时不触碰日志；`includeJournal=true` 时结果明确标注为日志；
26. 命中日志后能用 `J-...` 取到全文（`ids` 支持两种编号空间）；
27. 日志搜索支持 `dateFrom/dateTo` 过滤；
28. 搜索日志不增加长期记忆 usage；
29. 日志不会自动升级为长期记忆。

### Token 与缓存

30. 每轮模型调用不重复注入记忆索引；
31. 会话内写入或修改记忆不刷新系统上下文；跨午夜也不刷新；
32. 注入只包含标题，不含详细内容与日志正文；
33. 注入同时受 `maxSnapshotChars`(6,000)、`maxPinnedItems`(10)、`maxIndexItems`(100)、`maxJournalItems`(100) **四个上限**约束，且快照块字符数与**三段**的条数可逐项核对；
34. 截断按"整条省略、从尾部开始、置顶条不被省略"执行，并给出省略说明（§9.4）；
35. 同样的文件状态生成逐字符相同的快照（含空区段渲染规则）；
36. 会话恢复时快照按当时状态重建，且不产生两份索引的歧义。

### 安全与健壮性

37. 记忆与日志内容被明确标记为资料而非指令（含日志搜索结果）；
38. 敏感信息命中即拒绝整批写入，返回位置与类别且不回显原文；
39. 文件损坏不影响普通会话继续；
40. 批量操作不产生部分成功：**进程存活期内**任何失败都必须回滚到原样；**进程被杀**时允许出现"已生效子集"，但每个文件自身必须是语义完整的旧版或新版（绝不半条、半字段），且必须在下一个收敛点前前滚或回滚（§12.1）；
41. 多进程写入不静默覆盖，冲突时最多重试两次后明确报错；
42. 子代理只能只读搜索记忆，写入类工具不可见；
43. 降级告警出现在工具返回中，不只写进日志文件；
44. 超长条目不进入索引时，快照中必须出现"未索引条目"统计，且该说明行的文本与 §9.4 第 5 步逐字一致；**存在省略时 (a) 句的三个数字逐项可核对**（N 含被省略的置顶条，K = `min(M, maxPinnedItems)`，§9.4 第 5 步）；

### 复审补充（R1.3 第二稿及以后）

45. **主 agent 版**固定系统说明 + 固定工具速记合计 ≤3,000 Unicode 字符，且同一角色内会话之间逐字不变；子代理版单独满足 ≤3,000 且逐字不变；
46. 子代理收到的固定说明与工具速记中**不出现** `memory_write`／`memory_edit`／`memory_archive`／`memory_log` 四个名字；
47. `memory_edit`：编辑后编号与 `创建` 均不变；`detail: null` 后该条无 `详细`；`tags: []` 后标签为空；改 `kind` 后条目位于目标类型的 H2 分节下，渲染类型与 `kind` 一致；对归档编号编辑被拒绝；把 `expiresAt` 改成过去日期被拒绝；
48. 归档、`superseded`、派生 `expired` 的条目一律不进入注入与默认搜索（§14.10 只覆盖了 candidate）；candidate 条目归档后再恢复，`状态` 仍为 candidate 且不进入注入；superseded 条目归档后再恢复，`状态` 仍为 superseded 且不进入注入与默认搜索；
49. `INDEX.md` 列出全部非归档条目（含 candidate／superseded／expired），每行含 `★`／`（置顶）` 渲染、类型展示名、标题与中文状态写法，头部有 `next-id`，超限条目带 `⚠ 超限未注入`；删掉该文件后能从活动记忆重建出等价内容与等价顺序；
50. 降级路径可验收：`INDEX.md` 损坏后能重建；日志写入失败不阻塞当前模型步骤；`usage.json` 损坏只清空 usage，不影响注入；
51. §8.2 的约束可验收：对同一批结果里某条不相关记忆连续读取正文 20 次后，标题精确命中的条目仍排在它前面；**且这 20 次读取不改变下一次会话边界注入的顺序**（`usage` 不进注入链，§9.4）；
52. 敏感信息正反例各一条：标题含 `Authorization: Bearer abc123` 必须被拒绝，返回字段名与类别且不回显原文；标题为"如何配置 TOKEN 刷新流程"必须写入成功；
53. 编号降级路径：两处水位线同时丢失、且历史最大编号条目已被人工删除时，编号复用会发生，并在工具返回中告警；
54. 手工超限条目仍出现在 `INDEX.md`（标 `⚠ 超限未注入`），只缺席会话边界快照；
55. 工具返回（`memory_search` 的任何 `detail`）**不渲染 `★`**，只给 `[#编号]`；`★` 只出现在 `INDEX.md` 与会话边界快照里；
56. `INDEX.md` 的重建顺序符合 §2.3：**参与注入的**置顶条目在前，其后按 `active → candidate → superseded → expired` 分组，组内按 §9.4 排序链；同一条目不在 `INDEX.md` 中出现两次。

### 写入触发与提醒（R1.4 新增，对应 §17）

57. 一次交付只提醒一次；纯问答会话**零提醒**（一句提醒都不发）；
58. 同一轮内 `agent/turn-stopping` 被派发多次时也只提醒一次（交付标志"取出即消费"）；
59. 冷却命中时**放弃该发**：置 `taskReminded = true`（避免同一任务被反复求值时补发），但**不更新 `lastRemindTurn`**（这一发不构成冷却基准），也不补发；**这次放弃必须留下一条 warn**（现有实现没有这条日志，重写时要补，否则"为什么没提醒"无法排查）；
60. `payload.signal.aborted === true` 时不 steer；`turn` 不是正整数时跳过并记 warn；
61. 提醒消息的键集合恰为 `['content','id','role','source']` 且 `role === 'user'`（缺 `role` 会让上游拒绝整个请求）；
62. 子代理（含 `subagent_fork` 出来的子会话）永不提醒；`agent/disposed` 之后该会话的提醒状态被清理；
63. 只在 shell 里落盘、从未调用 `present` 的任务不提醒——这是**写进文档的已知代价**（§17.2），不得用"猜命令文本"来补。

### 越权编辑、可见性与原子性（R1.4 新增）

64. **越权手工编辑可告警**：模型用 write／edit／pwsh 直接给活动记忆加 `置顶：true`、手写 `next-id`、写超长标题、写重复编号时，下一次扫描必须在工具返回或会话边界告警里指出"检测到人工改动"及具体条目，并按 §2.3／§6.1／§5.6 的规则自愈（水位线取 `max`、重复编号修复、超限条目标 `⚠ 超限未注入`），**不静默接受、也不静默覆盖**；
65. 子代理的模型可见 schema 中**不含** `memory_write`／`memory_edit`／`memory_archive`／`memory_log` 四个名字，且即使强行调用也被拒绝（`tools.restrict({deny})` + `execute` 兜底两道，§7.0）；
66. **多文件原子性**：`.state/intent.json` 存在时进程被杀，下一次收敛点前滚或回滚到一致状态；任一时刻每个文件都是语义完整的旧版或新版，不出现半条、半字段；无法收敛时返回 `degraded` 并报出 intent 路径（§12.1）；
67. **`source` 映射生效**：`startup`／`resume`／`clear` 各按 §9.1 建快照；`'compact'` 到达时**不重建**（构造一次带 `compact` 的 `agent/created` 事件即可验证）；未知／缺失值在无快照时兜底一次并记 warn。

### 规则可执行性（R1.4 新增，来自 R1.3 的未闭合项）

68. **冲突与取代不再互相锁死**：写一条与 `#0011` 数值不同（3080→3180）的同主题记忆，第一通调用返回 `conflict` **并给出"重发并带 supersedes"的下一步**；第二通带 `supersedes:["#0011"]` 的调用成功且原子完成替换；同一批里被 supersede 的条目不再参与冲突判定（§7.1、§8.3）；
69. **解析契约不丢内容**：顶格字段行（`状态：active`）、Tab／全角空格缩进、续行内出现空行三类人工编辑，内容全部保留且各有一次 warn（§5.5 第 4、5、7 条）；
70. **`§14.5` 的机械写法可通过**：`别名：us` 这类标题不被误判为字段（§14.5）；
71. **`title` 校验机械化**：单行、非空、≤160 字可写入；空标题／换行／161 字被拒（`invalid_param`）；"完整陈述"不再是拒写条件、不进验收（§7.1）；
72. **恢复前置检查可判定**：归档条目字段合法时能恢复；`归档前状态` 取值非法时被拒并指出是哪一项不合格（§6.2）。

### 日志标题注入（交付后增补，§9.2）

73. **段与行格式**：`[项目日志]` 段渲染在 `[项目记忆索引]` 之后、说明行之前；每行逐字为 `[J-YYYYMMDD-HHMM] 标题`，**无类型标签、无 `★`**；同一分钟的 `-2` 后缀原样保留（`J-20260920-1752-2`）；
74. **最新优先且可复现**：段内按 `创建日期降序 → 同日 order 降序 → 编号降序` 排列；同一批文件（`M-` + `JOURNAL-` + `INDEX.md`）两次构建必须逐字符一致（§14.35）；
75. **条数上限**：`maxJournalItems = 100`（默认）；造 120 条日志时只注入 100 条，且**被省略的是最旧的 20 条**（保留排序链前缀）；
76. **关闭开关**：`maxJournalItems = 0` 时既不渲染 `[项目日志]` 段，也不产生 (c) 句；其余各行与未开启该功能时逐字符一致；
77. **共享预算 + 日志先让步**：`maxSnapshotChars = 6,000` 同时约束三段；预算不足时**先**省日志段尾部、日志段省空后**才**省索引段尾部；反过来，日志段**不因**索引段被截断而被整体省略（置顶 > 索引 > 日志）——两种方向都要有用例：① 日志很多 + 索引不多 → 索引段全部条目都在、日志被削；② 索引段把预算用尽 → 日志段为空且渲染 (c) 句；
78. **说明行 (c) 与正文隔离**：日志段有省略时，说明行必须以逐字文本 `另有 X 条日志标题未注入。` 报告，`X` = 可注入日志标题总数 − 实际渲染条数；日志的省略**不并进** (a) 句的 `N`；快照里**任何位置**都不得出现日志的 `内容／结果／决策／证据／后续` 字段文本（用"只在日志正文里出现的哨兵字符串"验证）。

## 15. R1 明确不做（有意留白）

- 每轮自动召回或注入；
- 把日志**正文**注入系统提示（**日志标题自交付后增补起随会话边界快照注入**：只注入标题、最新优先、上限 100 条且预算不足时先让步，见 §9.2／§9.4）；
- 用户级、全局级、跨项目记忆（跨项目知识统一放技能/团队文档，§2.4）；
- embedding、向量库、外部搜索服务；
- LLM 自动摘要、自动合并、后台遗忘；
- **模型置顶、自动归档**：`memory_*` 工具一律不提供这两个能力（**长尾记忆靠人工归档治理**，这是有意留白，不是遗漏）。注意"模型手里的通用文件工具能改文件"不等于"模型能置顶"——那由 §10.1 的禁令与扫描期校验约束（§1.4、§14.64）；
- **物理删除**：记忆误写走归档（§6.4）；日志误写 R1 **不提供删除或编辑**，唯一处置是**再追加一条更正日志**（说明哪一条作废、正确结论是什么），引用关系与时间线都留在文件里；
- 无提示地覆盖冲突事实；
- **语义相反的判定**（"必须重启"vs"不必重启"这类需要理解含义的冲突）——R1 只做 §8.3 里可机械判定的那一类；
- 把所有聊天内容自动写入日志；
- 一条记忆一个文件；
- 把 `candidate` 当类型；
- 用日志搜索次数影响长期记忆排序，或**用任何读取行为（含子代理读取）影响注入排序**（§9.4）；
- `memory_delete`（误写走归档，§6.4）。

## 16. 最终形态摘要

```text
<项目根>/memory/
├── M-YYYY-MM-DD.md          # 长期记忆：约定、事实、流程、经验
├── JOURNAL-YYYY-MM-DD.md    # 项目日志：过程、尝试、结果、证据
├── INDEX.md                 # 人类视图：活动长期记忆标题 + 编号水位线
├── archive/                 # 归档长期记忆
└── .state/                  # 可重建机器状态（水位线、用量、锁）
```

```text
会话开始/恢复：固定说明 + 固定工具速记 + 长期记忆标题快照 + 日志标题段（+ 截断说明）
会话进行中：不刷新；需要详情或过程时主动 memory_search
记录过程：memory_log
保存结论：memory_write
修正结论：memory_edit
替代旧结论：memory_write + supersedes（一次完成）
隐藏旧结论：memory_archive
任务交付完成：steer 一条提醒（§17），提醒不是指令、忽略无副作用
```

写入通道只有一条：`memory/` 下的 Markdown **只由 `memory_*` 工具写**；模型不得用通用文件工具直接改（§1.4、§10.1），人工改动会被扫描期校验告警并按规则自愈（§12.3）。

最终判断标准不是"记忆文件里存了多少东西"，而是：

> 模型在不增加每轮上下文成本的前提下，能稳定看到少量重要项目约定，并且在需要时能可靠追溯项目过去发生过什么。

## 17. 写入触发策略：交付完成提醒（R1.4 新增）

### 17.1 为什么必须有这一章

R1.3 只在固定提示词里交代"用户明确说记住就写"，把"什么时候该回想一下"交给了模型自觉。历史经验恰好相反：现有实现（`D:\dsh-memory`）立项的理由就是**把靠提示词约束维持的纪律改成由插件保证**——"交付后记得回写"这条纪律只写在提示词里时，会稳定地退化成"想起来才写"。

因此本插件对**任务交付完成**这一时机做**一次会话内提醒**：

```text
任务交付完成 → steer 一条提醒 → 模型用 memory_write / memory_log 落笔
```

三条边界先说清：

- 提醒**只推动落笔**，不决定记什么，也不替模型筛选内容；
- 提醒**不是系统指令**（§1.4）：它不能改变工具权限、不能放宽 §7.6 的敏感信息策略、也不能盖过用户的最新要求；
- 提醒**不改变已注入的快照**（§9.1）：它走会话内消息通道，不动系统提示词，前缀稳定性不受影响。

### 17.2 交付信号只有一个

| 项 | 规定 |
|---|---|
| 唯一信号 | `deliverables/presented` 会话事件。DSH 的 `present` 工具**只在成功呈现过文件之后**追加它，载荷为 `{ turn, callId, files }`——等于模型自己声明"这就是交付物" |
| 明确禁止 | 用命令文本、工具参数或正则**猜**"这次是不是在写文件／是不是交付"。历史故障：`ssh -G us 2>&1 \| Select-String …` 因为 `2>&1` 里的 `>` 被判定成"在写文件"，凭空触发一次提醒 |
| `tools/result` 的作用 | **只**用来标记"本轮出现过工具活动"（用于区分"还在干活的轮"与"静默收尾的轮"），不参与交付判定 |
| 已知代价（必须写进文档，不当 bug） | 只在 shell 里落盘、从不调用 `present` 的任务**不会**被提醒。**提醒宁可漏报，不要误报**；"交付时该调 `present`"的硬要求由**宿主自己的 `present` 工具描述**给出（实测 `dsh-tool-present` 的 description：When a file you create or update is an output the user asked to receive, you must call present…），**交付后按用户手改，本插件的固定提示词不再重复这句话**——两边是"同一要求、单一出处"的关系 |

### 17.3 判据与状态机（语义照搬已验证的实现）

事件时序是固定的四条，状态机必须按它推进：

```text
轮内   tools/result                → 标记「本轮有工具活动」
轮内   deliverables/presented      → 标记「本轮有交付物」（一次性，求值时消费）
轮末   agent/turn-stopping         → 推进状态，决定是否 steer
轮界   turn/start                  → 复位「本轮」两个标志
```

| 规则 | 规定 | 理由 |
|---|---|---|
| 复位时机 | "本轮"标志**只能在轮界（`turn/start`）复位**，不能按轮次号变化就地复位 | 被 abort／error 打断的轮不会派发 `turn-stopping`，只能靠轮界兜底；否则标志会漏到下一轮 |
| 交付标志 | `turn-stopping` 求值时**取出即消费** | 同轮内 `turn-stopping` 会被派发多次（steer 出来的额外步跑完会再派发一次），不消费会重复提醒 |
| 交付轮 | 进入 `awaitingClosure`、`taskReminded=false`、`idleTurns=0`；`completionIdleTurns ≤ 1` 时该轮即完成轮 | —— |
| 有工具活动无交付 | `idleTurns = 0`（任务尚未收尾） | —— |
| 静默轮 | `idleTurns += 1`，达到阈值即完成轮 | 覆盖"交付后不吭声直接结束"的收尾形态 |
| 提醒条件 | `completedNow ∧ !taskReminded ∧ remindOnDelivery ∧ 未命中冷却` | —— |
| **冷却命中** | **放弃这一发**：置 `taskReminded = true`（避免同轮被反复求值时补发），但**不更新 `lastRemindTurn`**（这一发不算冷却基准），也不补发；并记一条 warn | 补发既不要求任务完成、也不绑定任务，会落在"正在干活的轮"或"另一个任务"上；**漏一发只是少一次提示，多发一发才是真伤害** |
| 迟到交付事件 | `event.data.turn < lastEvaluatedTurn` 的事件不计，记 warn | 宿主顺序若变化要能察觉，而不是污染下一轮 |
| 轮次号校验 | 必须 `Number.isInteger(turn) && turn > 0`，否则跳过并 warn | `Number(null)`／`Number('')` 都是 `0`，只判 `isFinite` 会让"缺轮次号"蒙混过关 |

> 措辞纠正：现有实现的 README 写"冷却命中时提醒会**推迟补发**"，但它自己的代码是**放弃**（`delivery.js`：命中冷却时置 `taskReminded = true` 且不提醒）。R1.4 以**代码语义**为准——放弃不补发；重写时 README 必须同步改正，否则"文档说会补、实际不补"本身就是一次静默偏差。

### 17.4 投递形态（硬要求，缺一项就出事故）

提醒通过 `agent.steer(message)` 投递（会话内追加一条用户消息）。消息必须与 DSH 的 `UserMessage` 同形：

```json
{
  "id": "<随机 uuid>",
  "role": "user",
  "content": [{ "type": "text", "text": "<提醒正文>" }],
  "source": { "kind": "plugin", "plugin": "<插件名>" }
}
```

- **顶层 `role` 必填**：LLM 适配器原样透传 `message.role`，`undefined` 会被 `JSON.stringify` 丢掉，上游随即以 `messages[N]: missing field 'role'` **拒绝整个请求**——一次真实 P0。形状自查：键集合恰为 `['content','id','role','source']`。
- `payload.signal.aborted === true` 时**不 steer**（取消传播优先）。
- 提醒正文是**固定模板 + 当日文件名与路径**，并且**首行固定以 `[记忆插件]` 开头**——这个前缀就是 §10.1 里"收到 `[记忆插件]` 的交付提醒"所指的同一个标记，必须逐字固定、不随会话变化（前缀写死的理由：它是模型识别该消息的唯一凭据）；结尾必须允许忽略：本轮确实没有值得沉淀的内容，忽略它没有副作用。
- 提醒里只提醒两种落笔：可复用结论 → `memory_write`；过程与证据 → `memory_log`。**不**提醒归档、编辑或搜索，也不因提醒而放宽任何校验。

### 17.5 隔离与生命周期

- 只有**通过身份白名单的主会话**能收到提醒；判定必须用正向特征（lineage 显式顶层 + 白名单），不能用"某字段缺失"（缺省值会被持久化物化）。子代理与 `subagent_fork` 出来的子会话**永不提醒**。
- 每个会话一份独立状态；`agent/disposed` 时清理该会话的提醒状态与快照缓存；插件热重载时全部注册随 effect 撤销。

### 17.6 可配置项

| 配置键 | 默认 | 说明 |
|---|---|---|
| `remindOnDelivery` | `true` | 总开关；`false` 时完全不 steer（其余记忆功能不受影响） |
| `completionIdleTurns` | `1` | 判定"任务完成"所需形态：`1` = 交付轮当场算完成轮；`≥2` = 交付后再空转 N−1 轮才算完成 |
| `reminderCooldownTurns` | `1` | 两次提醒之间至少间隔的轮数（跨任务限流）；`0` = 不限流 |

### 17.7 提醒与其它机制的关系

- 提醒**不**触发 `memory_search`、`memory_edit`、`memory_archive`；
- 模型据提醒调用 `memory_write` 时，仍走 §7.1 的全套校验（重复／冲突／敏感／超长），命中即按错误码返回；
- 提醒发生的那一轮**不重建快照**（§9.1 不变量），要看新写入的值仍需 `memory_search`。

### 17.8 验收

见 §14.57–§14.63（交付轮提醒一次、纯问答零提醒、同轮只提醒一次、冷却放弃不补发、abort 不 steer、消息形状、子代理不提醒、只落盘不 present 不提醒）。

### 17.9 与现有实现的关系

这一章不是新发明：现有实现的交付判定与提醒状态机**已经是纯逻辑 + 16 条按真实事件形状驱动的用例**（`delivery.js` 及其测试），且用真实事件载荷验证过（`tools/result` 是 `(exec, result)` 双参、`session/event` 是 `(session, event)` 双参）。重写时**建议整块移植并保留其测试**，但有三处必须改：① 提醒文案——对齐 §7.1／§7.5 的两种落笔（结论走 `memory_write`、过程走 `memory_log`），并固定 `[记忆插件]` 前缀（§17.4）；② 提醒里提到的工具名；③ **轮次号校验与冷却日志**——现有实现的纯逻辑层只用 `Number.isFinite`（`0`、小数、负数会被放行），正整数校验只在装配层做，R1.4 要求把 `Number.isInteger(turn) && turn > 0` 提到状态机入口，并补上"冷却命中"的 warn（现实现没有这条日志）。见附录 D。

## 18. 记忆面板（三页：记忆 / 日志 / 图谱 + 行内展开，R1.4 新增）

### 18.1 这一章解决什么

前面十七章的"人类视图"只有一个：`INDEX.md`（§2.3）。它只列标题，正文要看就得去翻文件。
本章给会话区加一个 **「记忆」标签页**，把 `memory/` 下的 Markdown 真相源**只读**渲染出来给人看；
面板里分**三页**（记忆 / 日志 / 图谱），条目详情**行内展开**（不再有右侧常驻详情栏）。

它**不改记忆模型、不加第二份真相源、不引入任何新的写入通道**：数据源仍是 §2.3 的那几类文件
（`M-*.md` / `JOURNAL-*.md` / `archive/M-*.md`；`INDEX.md` 只作为"可被人打开的文件"，语义不解析，见 §18.3），
面板是"第二个视图"，不是"第二个库"。

面板以**只读渲染**为主形态，但**归档 / 恢复两个按钮**是它的写入口：它们**不经模型、不走提示词**，
直接经宿主 `/memory` 命令执行（§18.7），落盘仍由 §12.1 的写入事务保证。

> **视觉准则以 `docs/prototype/memory-panel.html` 为准**。那是一个自包含单文件原型（无外部依赖，
> 页内标明了"真实标题 + 样例关系"的数据边界），**评审通过后**才按它改插件实现；本章描述的是落地形态，
> 两者不一致时以原型为准（原型是定稿，实现是它的落地）。

### 18.3 只读边界（这一章最重要的一条）

面板的定位是**人看，不是人改**：

1. **只读渲染**：只读 `M-*.md`、`archive/M-*.md`、`JOURNAL-*.md` 的原文，以及一层**浅解析**结果
   （分节、条目行、字段行；口径见 §18.6）。
2. **不解析 `INDEX.md` 的语义**：`INDEX.md` 是 §2.3 定义的可重建派生物，头部 `next-id` 注记是编号水位线的第二份记录
   （§6.1）。面板**不读水位线、不比较一致性、不据此判定"索引落后"**，也不触发任何重建——
   这些是 `store.js` 的职责（`loadProject` 只读诊断、`syncAtBoundary`/`rebuildIndex` 负责写），面板一概不碰。
   面板连 `INDEX.md` 的**内容都不读**，只在列目录时认出这个文件名。
3. **面板自身不写文件**：不创建目录、不改编号、不动 `.state/`、不直接改 Markdown。归档 / 恢复是**唯一**的"改数据"入口，
   它也不是文件写入，而是**面板发一条宿主命令**（`/memory archive|restore`），由 §18.7 的命令层复用 `store` 走完整写入事务。
4. **失败只降级**：任何读取失败都渲染成"空面板 + 一行原因"，**绝不抛错、绝不静默**（§18.5）。

> 与 §1.4 的关系：§1.4 的不变量是"模型不得用通用文件工具改记忆"。面板不给人留这条捷径——
> 详情区那两个按钮**只发宿主命令**（§18.7），真正的写入仍走同一套 `store` 事务。

### 18.3.1 行身份（`rowKey`）：一条记录在面板里的唯一标识

面板**不能拿编号（`id`）当行的身份**：编号可以是 `null`（解析器明确支持无编号条目），同一编号也可能出现在不同文件里
（`parse.js` 只在写入侧保证跨文件唯一，手改或写入中断会留下重复）。所以面板用行身份：

```text
rowKey(entry) = filePath + '#' + order      // client/memory-panel.js:682-684
```

`order` 是**每文件内**序号，必须与 `filePath` 组合才唯一。这个键在三处**同源使用**——一处分叉就会出现
"点第二行、详情显示第一行、归档的却是第一行"这类错目标（复核的 P1）：

| 用途 | 位置 |
|---|---|
| React 列表 key（记忆行 `key: 'row-' + rowKey(entry)`） | `client/memory-panel.js:2208` |
| 展开状态（手风琴 `expandedKey === rowKey(entry)`，同时只开一条） | `client/memory-panel.js:2196-2216` |
| 行高亮（展开区 `.dshmem-exp` 的左侧 2px 强调竖线 + `aria-expanded`） | `client/memory-panel.js:2210`、`:2228-2246` |

日志事件（`key: 'ev-' + rowKey(journal)` `:2294`；展开集合 `openEvents` `:2281`）与图谱节点
（节点 `id` `:1377`；React key `:2378`）用的是同一个键。图谱另有一张"编号 → 节点"的映射表
（`:1398-1410`）——关系是按 `#编号` 写的，节点身份是行身份，两者必须靠这张表对接。

理由与依据写在实现注释里（`client/memory-panel.js:669-677`）。

> **配套纪律（P1，同一个"错目标"缺陷踩过两次）**：展开区里的**归档 / 恢复 / 建议指令**必须用
> **当轮固定参数**绑定——要么用行身份 `rowKey(entry)` 做选中键，要么在渲染该行时用**立即执行的闭包**把 `entry`
> 钉住（实现即 `(function (entry) { … })(group.items[i])`，`client/memory-panel.js:2192-2247`）。
> **禁止**让 `onAct` / `onAsk` 直接捕获 `for (var i …)` 的循环变量：`var` 是函数作用域，回调会读到
> **循环结束后**的那一条——实测症状是"展开 #0001 点归档，发出去的是 `archive #0004`"。
> 这与本节前面"按 `id` 匹配"是同一缺陷的两种形态（见记忆 #0029）。

配套一条：条目上的 `filePath` 现在是**工作区相对路径**（`memory/M-2026-09-20.md`、
`memory/archive/M-2026-09-20.md`，`client/memory-panel.js:855-859`），不再是裸文件名——
否则活动区与归档区同名文件会撞 key。**归档分组**也因此是两部分的并集：`archive/` 下的文件，
加上仍写在活动文件里、状态为 `archived` 的条目（`groupByKind` `:1296-1300`；UI 调用 `:2151`）。

### 18.4 数据通路（远端只读面）

面板**不读文件系统**，走宿主给的 `workspaceFiles` 远端服务（与侧边栏文件页同一个面）。
客户端拿到的不是裸值，而是**结果信封**：`{ ok: true, value }` / `{ ok: false, error: { code, message } }`——
实现按 `result.ok` 判定，失败时把 `result.error.code` 包成带 `code` 的 `Error` 上抛
（`client/memory-panel.js:764-807` 的 `listDir` / `readText`）：

```js
// 列目录（拿文件名清单）
const listing = await ctx.remote.workspaceFiles.list(sessionId, "memory", signal);
// 成功 -> { ok: true, value: { path: "memory", entries: [{ name, type, size? }], truncated } }
// 失败 -> { ok: false, error: { code: "workspace-file/not-found", message } }

// 读文件：**只发 offset，不发 limit**（页长由宿主的 maxLines 决定）
const page = await ctx.remote.workspaceFiles.read(sessionId, "memory/M-2026-09-29.md", {
  offset: 1,
}, signal);
// 成功 -> { ok: true, value: { absolutePath, version, bytes?, offset, text, lines, eof } }
```

> **为什么客户端故意不发 `limit`**（值得记的坑）：页长由宿主的 `maxLines` 配置决定，
> 而宿主对 `limit > maxLines` 直接抛 `gateway/bad-request`（`dsh-api-workspace-files/lib/index.js`）。
> 一旦客户端把页长写死（硬编码某个具体行数），某天有人把 `maxLines` 调到它以下，**整个面板就会变成"读取失败"**。
> 官方客户端同样刻意不发 limit（`dsh-client-ui-sidebar-documentpreview/lib/client.js`：
> "The page length is the Host's configured cap, so no limit travels"）。
> 客户端只保留一个**翻页保险丝** `MAX_READ_PAGES = 200`（`client/memory-panel.js:91-100`）：
> 熔断时该文件按"只读了前 200 页"处理，并在通知区提示"文件过长，只读了前 200 页：<相对路径>"
> （`client/memory-panel.js:857`、`:881`）。

**路径是工作区相对路径**（`memory`、`memory/archive/M-2026-09-28.md`），由宿主按 `workspaceRoot` 解析。
依据（`dsh-api-workspace-files/lib/index.js`）：

- `inspect()`（:562-573）对目标做 `this.ctx.fs.lstat(path, { cwd: workspaceRoot }, signal)`；
- `confine()`（:575-582）用 `this.ctx.fs.resolve(path, { cwd: workspaceRoot, signal })` 再 `contains(root, target)` 判越界；
- `workspaceRoot` 来自会话头：`header.cwd ?? sandboxPolicy.workspaceRoot`（:404-414 的 `workspaceFileScope` lookup）。

分页口径（`dsh-api-workspace-files/lib/types/types.d.ts:31-55`）：行号 **1-based**、末行以 `\n` 结束；
`offset` 缺省 `1`；`limit` 缺省即宿主的 `maxLines`（默认 5000，`lib/index.js:383-388`），**面板不传它**。
`list` 的 `entries[].type` 只有 `file | directory | other`，符号链接报**目标**的类型（`types.d.ts:82-95`），
`truncated` 表示条目上限截断（默认 `maxEntries = 2000`）。

面板的取数顺序固定为（`client/memory-panel.js:819-910` 的 `loadModel`）：先 `list('memory')` 一次拿到全部名字 →
挑出 `M-*.md` / `JOURNAL-*.md`（**只有文件名有用：`INDEX.md` 连内容都不读**）；
目录里出现 `archive/` 时再 `list('memory/archive')` 取归档文件；每个文件按 `read` 翻页到 `eof`
（保险丝 `MAX_READ_PAGES = 200` 页）。单次加载每类文件最多读 `MAX_FILES = 200` 个
（`client/memory-panel.js:103`）。**所有截断都会在面板底部通知区显示，不静默**——`list` 的 `truncated` 两处、
三类文件的条数上限、超页数（见 §18.5）。
**进入视图、点「刷新」、归档 / 恢复成功后各拉一次**；面板不缓存、也不订阅 `changes`（§18.8 第 3 条）。

### 18.5 失败态口径

远端错误码与 `details` 是稳定的（`dsh-api-workspace-files/lib/types/types.d.ts:139-172` 的
`RemoteErrorDetailsMap`），客户端把它们包成带 `code` 的 `Error`（§18.4）。面板的处置其实只有两档
——**只有"目录不存在"是空态，其余一律错误态**：

| 情形 | 宿主错误码 | 面板表现 |
|---|---|---|
| 项目还没用过记忆（`memory/` 不存在） | `workspace-file/not-found` | **空态**："该项目还没有记忆目录（memory/）。用记忆工具写入第一条后回来刷新。"并附一句"面板只读 `memory/`；若本项目把配置 `memoryDirName` 改成了别的目录名，面板目前看不到内容。"（**正常状态**，不是故障；`:2108-2118`） |
| 其余任何读取失败：不是目录 / 不是普通文件 / 不是 UTF-8 文本 / 超字节上限 / 越界 / 传输失败 | `not-directory`、`not-regular-file`、`not-text`、`too-large`、`outside-workspace`、任意 | **错误态**：整块显示"读取失败：" + 消息；点「刷新」重试（不自动重试） |
| 解析期降级（畸形行、未知分节、缺字段…） | —— | **不中断渲染**：把告警码去重后汇总到通知区"解析告警：…"（`empty-file` 不算；`:895-899`） |
| **任何截断**（不再静默） | —— | 通知区逐条显示：`list` 的 `truncated`（`memory/`、`memory/archive/` 各一处，`:822`/`:843`）、三类文件的条数上限（记忆/归档/日志各一条，`:868`/`:872`/`:877`）、翻页保险丝熔断"文件过长，只读了前 200 页：<相对路径>"（`:857`/`:881`） |
| 归档 / 恢复命令 | —— | **受理口径**（见 §18.7）：`result.ok === true` 且 `matched !== false` → "已提交归档 #0012；结果见对话流"；`matched === false` → "宿主未识别该命令（可能是不支持 /memory 的旧版本）"；RPC 本身失败 → "命令失败：…"（`:1789-1823`，即 `act()` 全段） |

两条纪律：① **不做逐文件容错**——一个文件读失败会让整块面板进错误态，而不是"跳过它继续渲染"；
② 面板不因为失败去写盘，也没有"修复"这个动作。

### 18.6 格式口径：以 `src/parse.js` 实际行为为准

面板的浅解析必须与**真解析器**一致，不能照抄 §5 的样例就下笔。
本节及面板的全部格式口径**以 `src/parse.js` 的实际行为为准（设计 §5 的样例描述已过时）**，已核对到的三处差异：

| # | `src/parse.js` 的实际行为 | §5 的写法 | 位置 |
|---|---|---|---|
| 1 | 字段行**不要求缩进**，且列表标记可选：`  - 状态：active`、`状态：active`、`\t- 详细：…` 都能解析；中英文冒号均可 | §5.5 第 3 条写作"字段行形如 `<缩进>字段名：值`" | `matchFieldLine`（`src/parse.js:191-199`） |
| 2 | 缩进深度 = 把 Tab、全角空格各折算成 **2 个半角字符**后的**长度**，再按数值比较 | §5.5 第 4 条写作"按相对深度判定，不按字符数比较" | `depthOf`（`src/parse.js:177-180`）+ `titleDepth` / `lastFieldDepth` 比较 |
| 3 | 日志字段行必须**顶格**且以 `-`/`*` 开头（`^[-*]\s*名称[：:]\s?值`），无字段名的续行并入上一字段 | §5.4 只给了样例，没写这条 | `parseJournalFile`（`src/parse.js:950-967`） |

面板需要一致的最小集合（其余一律不认）：

- **长期记忆文件**：H1 `# 记忆 · <日期>`；H2 分节名取 `约定/事实/流程/经验`（未知分节按「事实」，同 `parse.js:405-411`）；
  条目行 `- [#0007] 陈述`（编号可缺，`-`/`*` 均可）；字段行按上表第 1 条识别，已知字段名以 `src/parse.js:116-141`
  的 `KEY_FIELD` 为准；`详细` 的多行值按"更深一级"的续行拼接。
- **日志文件**：H1 `# 项目日志 · <日期>`；分节 `## J-YYYYMMDD-HHMM · 标题`（正则见 `src/parse.js:153`）；
  字段为**有序** `- 名称：值` 列表（`JOURNAL_FIELD_NAMES`，`src/parse.js:147`），正文取值优先级
  `内容 → 详细 → 结果`（`src/parse.js:973` 的 `entry.content`）。
- **缺省值**（`src/parse.js:580-611` 的 `newEntry`）：状态 `active`、置顶 `false`、
  优先级按类型（约定 `high`，其余 `medium`，`KIND_DEFAULT_PRIORITY`）、置信度 `observed`、
  创建/更新 = 文件名日期（`M-YYYY-MM-DD.md`，`fileDateOf`）、有效至 `永久`。
- **状态**：面板展示 `状态` 字段的**原值**（`active / candidate / superseded / archived`）；`expired` 是**派生**状态
  （`isExpired` + `effectiveStatus`，`src/parse.js:281-299`），**面板不计算它**——派生只影响注入与搜索的可见性，
  面板回答的是"文件里写了什么"。
- **告警码逐一对齐**：面板的解析移植与 `src/parse.js` 的告警集合一致——包括日志侧的两个码
  `journal-no-content`（`client/memory-panel.js:627`）与 `duplicate-journal-id`（`:638`）。

  比对 `entries / warnings / preamble / damaged`（实现注释见 `client/memory-panel.js:15-18`），防止移植漂移。

面板**不解析**的东西：`INDEX.md` 的 `next-id` 注记与行尾标记、`.state/` 下任何文件、未知字段的语义

### 18.7 写路径：面板只有一条命令出口

面板**不写文件**，但它**有一条写入口**：详情区的「归档 / 恢复」按钮。

```text
按钮点击
  → buildActionLine('archive'|'restore', id, reason)                    // client/memory-panel.js:735-745
  → sessions.using(sessionId, { source: 'memoryPanel' },
        ref => ref.binding.session.command(line))                       // :1492-1500
  → 宿主命令 /memory 的 handler（createMemoryCommand，src/tools/archive.js:261-284）
  → runArchiveAction（与 memory_archive 工具**共用同一实现**，:79 / :251 / :274）
  → store.applyBatch（§12.1 的锁 / intent / 编号水位 / INDEX.md / .state/ids 一条不少）
```

| 动作 | 通道 | 落盘实现 |
|---|---|---|
| 归档 / 恢复（**面板按钮直接发起**） | 面板 → 会话命令 `/memory archive <#NNNN> [原因]`、`/memory restore <#NNNN>` → 宿主命令 handler | `src/tools/archive.js` 的 `runArchiveAction`（与 `memory_archive` 工具共用）→ `store.applyBatch` |
| 改 `详细` 正文、改标题 / 类型 / 状态 | 对话里调用既有 `memory_edit`（**不在面板内做**） | `store.applyBatch` 的 `edit` 分支 |
| 写入新结论、追加日志 | `memory_write` / `memory_log` | 同上 |

- **按钮提示只是"受理"、不是"成败"**：`session.command(line)` 返回的是**准入结果**（`RemoteResult`），
  `ok === true` 只说明命令**被受理**；宿主 handler 的 `{ kind: 'success' | 'error', text }` 会作为
  **对话流节点**呈现，**不回传面板**。所以按钮成功时的提示固定是"**已提交归档 #0012；结果见对话流**"
  （`client/memory-panel.js:1804-1812`）——面板**不声称**落盘成功；只有 `matched === false`（宿主不认识
  `/memory`，旧宿主线）与 RPC 失败才在面板上另说（`:1805-1806`、`:1814-1821`）。
- **命令语法与解析**：`parseMemoryCommand(rawInput)`（`src/tools/archive.js:231-245`）只认
  `archive <#NNNN> [原因]` 与 `restore <#NNNN>`；参数不合规返回 `kind: 'usage'`（当成功文本回面板），
  编号缺失返回 `kind: 'invalid'`（转成 `{ kind: 'error', text }`）。handler 内部 try/catch，
  任何异常都转成 `{ kind: 'error', text }`，**绝不外抛**（:255-283）。
- **`detail` 正文编辑不做进面板**：§5.5 第 5 条要求"工具侧必须当场拒绝含空行 / 项目符号分行的 `detail`"，
  这个校验住在工具层；面板若自己做文本框，等于绕过它。因此面板只给**只读正文**，要改就在对话里说。
  （面板里唯一的输入框是「归档原因」。）
- 命令的注册方式是**可选注入**（deferred inject），不是硬依赖。实测实现（`src/index.js:169-186`）：

  ```js
  const injectFn = ctx.inject;                     // 必须是方法：解引用会丢 this
  if (typeof injectFn === 'function') {
    ctx.effect(
      () =>
        injectFn.call(ctx, ['commands'], (childCtx) => {
          const commands = childCtx?.commands;
          if (commands === undefined || typeof commands.register !== 'function') {
            ctx.logger.warn('memory: commands 服务不可用，/memory 命令未注册（五个工具照常可用）');
            return;
          }
          childCtx.effect(() => commands.register(createMemoryCommand(deps)), 'dsh-memory: /memory 命令');
        }).dispose,
      'dsh-memory: /memory 命令',
    );
  }
  ```

  三条要点：

  1. `ctx.inject` 是 Context 上的**方法**（实现体是 `this.plugin({…})`），必须 `injectFn.call(ctx, …)`；
     解引用成 `injectFn(…)` 会丢 `this`，真机直接抛
     `Cannot read properties of undefined (reading 'plugin')`
     （签名：`@deepseek-ai/cordis/lib/types/registry.d.ts:185`；`plugin(` 见同文件 `:198`）。
  2. 取回调返回 fiber 的 **`.dispose`** 当 effect 撤销器——官方同款写法见
     `dsh-agent-loop/lib/index.js:1570-1579`。
  3. 插件的 `export const inject` **保持 `['systemPrompt', 'tools']` 不变**（`src/index.js:43`）。
     宿主不提供 `commands` 时回调根本不执行 → 旧宿主线**自动降级**为"有工具、没有 `/memory`"，
     不需要写任何版本判断（另一个同款范例：`dsh-api-gateway/lib/index.js:623,626`）。

  命令服务定义：`@deepseek-ai/dsh-commands` 的 `lib/types/index.d.ts:38-55`（`CommandDefinition`：
  `name` 不带斜杠、`description` 必填）、`:94`（`register(definition)` 返回撤销函数）、
  `lib/types/types.d.ts:34-39`（`CommandResult = { kind:'success'|'error', text }`）。

### 18.9 与其它机制的关系

- **不动注入**：面板纯客户端，不参与 §9 的会话边界快照，也不改前缀稳定性。
- **不动交付判定**：面板既不产生 `deliverables/presented`，也不消费提醒（§17.2 的唯一信号仍是 `present`）。
- **不动权限模型**：命令 handler 复用工具层的会话闸门 `checkCall`（`src/tools/archive.js:252-253` 的注释、`:273` 的调用），
  子代理与未登记会话在面板上点「归档 / 恢复」同样被拒——与"四个写入类工具在子代理侧不可见"同一口径（§7.0）；
  面板自身没有任何权限判断，它只是把一行命令交给宿主。
- **不加新配置键**：面板不引入任何 `config` 项（唯一的隐性前提是目录名必须叫 `memory`，见 §18.8 第 1 条）。

### 18.10 验收

1. 会话区出现「记忆」标签（`label` 硬编码为"记忆"），位置在「轨迹」右侧（`order = 20`）；
2. 面板有**三页签** `记忆 / 日志 / 图谱`，顶栏一行统计（`N 条 · 注入 X / Y 字`，`N`/`X` 均只算参与注入的条目、归档另以 `· 归档 M` 单列）+ **2px 三段预算条**；
   条目详情**行内展开**（手风琴，同时只开一条），**没有**右侧常驻详情栏（§18.2.1/§18.2.2）；
3. `memory/` 不存在时进空态，文案含"该项目还没有记忆目录（memory/）…"与 `memoryDirName` 提示，不报错、不建目录；
4. 记忆页分组为 约定/事实/流程/经验 + 归档（**归档默认折叠**），组头显示 `名称 · 条数 · 该组注入字数`；
   归档组含**仍写在活动文件里**的 `archived` 条目；
5. **行身份可靠**：存在无编号条目或同编号跨文件重复时，点哪一行就展开/操作哪一行（`rowKey = filePath + '#' + order`，§18.3.1）；
6. 日志页按日期倒序排成时间线；展开一条**逐行显示它的全部 `fields`**（长文本完整换行），且 `content` 不会重复显示一遍（§18.2.3）；
7. 图谱页：节点按类型分簇、半径随单条注入字数变化；边分 `rel`/`sup`/`log` 三类；可拖拽（位移 >2px 才算拖，否则算点击）、
   点节点在**图下方**展开详情、`含日志 / 关联 / 重置布局` 三个开关可用；重置丢弃拖动坐标（§18.2.4）；
8. 点「归档 / 恢复」后的提示是"已提交归档 #0012；结果见对话流"（受理口径，不含落盘成败结论，§18.7）；
9. 面板自身**不写文件**：唯一的改数据动作是发一条 `/memory` 宿主命令（§18.7）；样式表以 `data-dsh-memory="panel"` 标记且可卸载（§18.2.5）；
10. 手工把 `M-*.md` 改成畸形内容：面板显示已解析到的部分，并把告警汇总成通知区"解析告警：…"，不崩、不抛错；
11. 目录条数、每类文件数（200）、翻页页数（200）任一被截断时，面板底部都有对应通知，**不静默**（§18.5）；
12. 宿主缺 `commands` 时插件加载不失败、五个工具照常工作；面板点归档得到"宿主未识别该命令"提示；
13. 界面中文（§18.8 第 7 条为已知取舍）。

### R1.4 没有改、但需要你裁决的一项

**旧记忆文件的处置**：现有实现按 `M-YY-MM-DD.md`（如 `M-26-9-20.md`）写、分四区 `偏好／事实／知识／反思`；R1.4 改为 `M-YYYY-MM-DD.md` + `约定／事实／流程／经验` + 编号。二者**不兼容**，且设计里没有约定如何处理历史文件。三种可选做法（本设计不替用户决定）：

1. **丢弃**（R1 阶段的旧稿选过这条：旧内容整体移入 `backups/`，新格式从零开始）；

3. **原样共存**（旧文件不迁移、也不参与解析——**代价**：旧条目在 `INDEX.md` 里消失、也不会被索引或搜索到，等于静默丢失，与 §1.4 的"绝不静默"冲突，不推荐）。
